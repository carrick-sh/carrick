# K2 scoping — what the fork memory path actually does today

**Recorded 2026-08-13**, after K1 GO (`7b808b6cf`) and the boundary number
(4.410 CPU-s, 2.574x Docker on the workload window).

Everything here is READ FROM CODE with exact `file:line`, then adversarially
verified. Nothing in this document is measured; the "Measure first" section
says what to run before ranking levers, and that must happen before any lever
is chosen.

## The structural finding

Every HVPatch process carries a **32 GiB `mmap` arena as ONE boot region**
(`carrick-mem/src/memory.rs:3215-3223`, `LINUX_MMAP_SIZE = 32 GiB` at
`memory.rs:364`), plus a 2 GiB private overlay and a 128 MiB heap — about
**34.2 GiB of private virtual span per process**. That is why the process
bank is 40 GiB.

Fork, exec and exit each do whole-span work over it:

| Operation | Per event | Count on the fixture |
| --- | --- | --- |
| `mach_vm_remap(copy=TRUE)` over the full 32 GiB arena | `trap.rs:6265` | 68 forks |
| Rebuild **16,384 L2 block descriptors** for the arena in the child's stage-1 | `trap.rs:6312` → `page_table.rs:937-944` | 68 forks |
| `hv_vm_map` of 32 GiB | `trap.rs:6471` | 68 forks |
| Unmap 32 GiB, mmap 32 GiB, map 32 GiB | exec path | 67 execs |
| Unmap 32 GiB | exit | 69 exits |

This is verbatim what K2's gate forbids: *"Fork work scales with writable
table paths/touched frames, not virtual span."*

## Answers to the four questions K2 needs

1. **Is there a whole-address-space `mach_vm_remap`?** No — but there is one
   **per private mapping**, and its `size` argument is that mapping's full
   virtual span, including the 32 GiB arena in a single call
   (`trap.rs:6264`). The gate's literal wording is already satisfied while
   its substance is not.
2. **Is a flat page-table image published per fork?** **Yes.** The full
   `LINUX_PAGE_TABLES_SIZE` = 0x1C0000 = 1.75 MiB is `copy_nonoverlapping`'d
   into the child's backing at `trap.rs:6381-6387` regardless of how many
   descriptors differ. Note the child's table backing is itself a COW remap
   that this memcpy then dirties in full, so its COW buys nothing.
3. **What is O(virtual span) vs O(touched frames)?** O(span): the
   `map_aliased` re-pointing loop (16,384 L2 writes plus 16,384
   `descend_creating` walks for the arena alone), the `remap_copy` size
   argument, the 1.75 MiB table copy, and the mincore vector in the fallback.
   **O(touched frames): nothing.** Nothing today is per-page-touched.
4. **Is there real COW?** Yes, but **host-side only**:
   `mach_vm_remap(copy=TRUE)` at `carrick-host/src/host_mapping.rs:112`, at
   host 16 KiB granularity. There is **no guest-visible / stage-1 COW**: the
   child's stage-1 leaves are built read-WRITE for every writable mapping
   (`trap.rs:6312-6317` passes `mapping.guest_writable` straight through), so
   no guest store ever takes a COW fault and the parent's tables are never
   write-protected. Building that is K2's core work.

## An important negative result

`hvpatch/banked_mm.rs` and `hvpatch/bank_resources.rs` do **no memory work at
all** — no mapping, no copy, no page enumeration. They are pure bookkeeping
(ASID allocator, an 11-entry bank free-set, `MmBinding` publication). Nothing
anywhere expands a bank into 16 KiB records: the 40 GiB bank is a
cursor-packed IPA reservation (`trap.rs:6252-6262`) and the frame inventory is
keyed by **extent** `(ipa, size)` (`trap.rs:6220`), not by frame.

So the K1 spec's "expanding it eagerly would create 2,621,440 records" hazard
is a hazard **of the proposed K2 design**, not a cost being paid today. K2
must not import it.

## A second bucket that is NOT K2's

Roughly 8-10 shared-lock acquisitions per Linux syscall on state now shared by
all 69 guest processes in one host process. The clearest instance:
`ProcessContext::syscall_trace_identity()` (`vcpu_loop/mod.rs:3031-3043` →
`hvpatch/mod.rs:170-174`) takes a registry read lock and an mm-binding read
lock and is computed **unconditionally on every syscall**, before the USDT
enabled-gate that exists to make it free.

That violates this tree's own stated contract (`probes.rs:3455`, and the
worked example at `probes.rs:4428-4436`): the expensive work belongs INSIDE
the probe closure, which `usdt` only invokes when a consumer is attached.
Fixing it means letting `hvpatch_syscall_service_begin` resolve identity
lazily inside the closure. **This is K5 (syscall lowering), not K2** — it is
recorded here so it is not lost, and so K2 does not take credit for it.

## Measure first — do not rank levers from this document

Per-stage probes already exist and need no new instrumentation:
`HvpatchForkProcessSpecStagePhase::{ParentPageTablesClone, PageTablesRebase,
AliasUnion, PrivateSnapshot, Validation, TablePublish, BackendProtections,
BackendSpecFinalize, Total}` and `HvpatchForkRuntimeStagePhase::*`. One signed
`carrick trace` run over the 68 forks gives the real split.

Four things this scoping could not answer, each directly measurable:

- The true cost of `mach_vm_remap(copy=TRUE)` on a 32 GiB span. Mach's
  delayed-copy cost scales with the source range's VM map **entry** count,
  which depends on how fragmented the arena is at fork time — a live
  measurement, not a code-reading answer.
- How often the span-proportional fallback (`clone_region_for_child`,
  `trap.rs:8038`) actually fires. `HvpatchForkPrivateSnapshotMethod::{MachCowRemap,
  SparseCopyFallback}` (`trap.rs:6272-6276`) already distinguishes them. If the
  fallback fires on this lane at all, the O(span) memcpy story is far worse
  than the happy path suggests.
- The real entry count in `self.mappings` at fork time — already emitted as
  `local_regions`/`candidate_regions`/`added_regions` by
  `hvpatch_fork_snapshot_end` (`trap.rs:6394`).
- The exec-side memory cost, uncovered by this pass. With 67 execs against 68
  forks it is plausibly the same order as the fork side.

## Already-disproved lever

Removing the gratuitous 1.75 MiB `page_tables.clone()` per fork (`ba26307a5`,
~238 MiB per build) produced **no measurable change**: 4.44 CPU-s mean against
a 4.410 baseline. Bulk memcpy of the table image is not where the CPU goes.
K2's lever is the structural change — persistent refcounted table pages whose
fork cost tracks the writable paths actually touched, and a remap that names
touched frames rather than a 32 GiB span — not "copy less".

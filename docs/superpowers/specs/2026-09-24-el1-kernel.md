# The EL1 kernel: Carrick's kernel runs in the guest, the host is the platform

Status: ACCEPTED by the owner, 2026-09-24. Carrick's direction is an EL1
kernel. This supersedes stages 2-4 of
[`2026-09-24-zone-the-workloads.md`](2026-09-24-zone-the-workloads.md); stage 1
(the file zone) and the memory-bookkeeping fixes stand. Acceptance commits to
the direction and the migration order, not to every detail below: each
increment still lands only with its red-first contracts, census and signed
gates, and the open items under "Before acceptance" are now entry criteria for
the increments that depend on them.

## Decision requested

Stop moving objects into EL1 one at a time with no end state. Adopt an end
state in which Carrick's kernel executes at guest EL1 and owns every object
that never leaves the Linux compat zone, and the host process is a platform:
vCPUs, bulk memory, host files, host sockets, clocks. Migrate to it subsystem
by subsystem, deleting each host implementation as its EL1 replacement lands.

## Evidence

All measured on Apple M4, macOS 27, signed builds of local main. Single runs
unless stated; "suggests" where the method is not a controlled experiment.

| Finding | Evidence |
|---|---|
| Two owners per object is where the defects are | This campaign's defects were coherence between host and EL1 or host-process-shaped authority: delegate/recall (abandoned), lazy member detach, the mailbox-slot cache that served one process's files to another (`fd11bd8cc`), the discard/COW shadowed-row lookup |
| Moving single objects wins locally, not on workloads | inotify09 2.7 s vs 36 s with EL1 off; the ecosystem census shows the zone's classes are a small share of host syscall CPU ([census](../../perf-results/2026-09-24-el1-census.md)) |
| Exits themselves are small | VM exit/entry plus register sync: about 6% of carrier CPU on both go build and cpython (profile, below) |
| Host thread scheduling is large on Go | go build (hello, cold cache): executor block/wake, condvar and scheduler locks = about 24% of carrier CPU; guest execution 31% |
| Memory bookkeeping is large on Python | cpython tests: fault/COW service 26% and mm syscalls 14% of carrier CPU, mostly Carrick user-space index walks (being fixed now, independent of this design) |
| Guest EL1 can own stage-1 | spike `spike/el1-tlbi-stage1` `18ffa1c51`: broadcast TLBI invalidates sibling vCPUs with no host action (0 stale of 370M reads at 8 vCPUs; control without TLBI: 91% stale); EL0 translation faults are taken at guest EL1 with no exit |
| In-guest fault service is cheaper and removes the pause | first-touch fault in EL1 190-250 ns vs 0.9-1.3 µs host-resolved without any pause; host pause of 8 vCPUs p99 0.3-1.6 ms (tail up to 3.3 ms), the mechanism behind the `fault page-table pause ... TimedOut` guest crashes |

Profile method: `profile-997` on the carrier, samples split into guest
execution (the qualified HVF guest PC), host kernel and user, user stacks
symbolized offline and bucketed by frame. Scripts are scratch today and become
a `carrick trace` profile before this design is accepted (Rust-first rule).

## Goal and the premise it must keep

Goal: correctness by construction (one owner, one implementation per object)
and host-native cost: within 2x of native-arm64 Docker per row, no
load-dependent verdicts.

Carrick's premise constrains the design. It must keep:

- **Host scheduling of CPU.** vCPUs are host threads the host schedules; an
  idle vCPU costs nothing. No fixed guest CPU reservation.
- **Elastic memory.** The host grants frames on demand and the guest returns
  free frames promptly. No fixed-size VM RAM pool sized up front.
- **Host-native I/O.** Files are host files (bytes on APFS), sockets are host
  sockets, clocks are host clocks.
- **Honest status.** An EL1 kernel is guest-reachable privileged code; this
  design does not make a guest a hardened trust boundary (see Security).

## The host interface

One narrow hypercall ABI (HVC with a request ring in shared memory), versioned
by the existing ABI layout hash.

- **Classes:** file-bytes (read/write/fsync by host handle and offset),
  namespace (open/stat/rename/unlink/mkdir/link/xattr by contained parent
  handle and leaf), socket, memory (grant/reclaim frame extents), clock
  calibration, vCPU (park/wake), process-boundary (core file, exit status to
  the CLI).
- **Asynchronous by default.** A host request does not hold the vCPU: EL1
  queues it, switches to another runnable guest thread, and resumes the waiter
  on completion. This is what the current continuation machinery does in the
  host; in the end state it is EL1's ordinary blocking.
- **Batched.** Requests and completions travel in rings; one exit can carry
  many requests, and a busy vCPU need not exit to learn of completions.
- **Validated.** The host treats every request as untrusted input (guest EL1
  is guest-reachable). Path containment, handle ownership and quotas are
  enforced host-side, as the host backends enforce them today.

## Scheduling

- Each vCPU runs an EL1 scheduler over the runnable guest threads it owns; a
  context switch is register save/restore and a TTBR/ASID switch at EL1, not a
  host condvar.
- Preemption uses the guest virtual timer (CNTV) delivered at EL1.
- A vCPU with nothing runnable parks in the host (WFI or HVC exit); the host
  thread sleeps. Waking a parked vCPU is the only host involvement in guest
  scheduling.
- Load balancing across vCPUs is EL1's (work stealing between per-vCPU run
  queues); the host's scheduler still decides which vCPU threads run.
- The vCPU count stays elastic: the host adds vCPUs up to the core count and
  retires idle ones.

Measured (scheduler spike, `spike/el1-scheduler` `c9897ae4c`, Apple M4,
macOS 27.2, shared host at load 3-6):

| Operation | Cost | Host exits |
|---|---|---|
| EL1 thread switch, same address space | 28 ns p50 | 0 |
| EL1 switch, other address space (ASID, no flush) | 42 ns; 54 ns with FP/SIMD | 0 |
| Switch with a TLB flush (the control) | 190-440 ns | 0 |
| Timer preemption via `hv_gic` (vtimer PPI 27 at EL1) | deadline to handler under 42 ns p50 | 0 |
| Timer preemption without the GIC | 1.0-1.5 µs p50 | 2 per tick |
| Wake a vCPU parked in WFI, by SGI | 6-10 µs p50 (4 µs with a time-constraint thread policy) | 0 to our process |
| Wake a running vCPU, by SGI | 1.8-2.0 µs p50 | 0 to our process |
| Today: host condvar round trip | 2.3 µs p50 | n/a |
| Today: guest futex ping-pong under Carrick | 26-31 µs mean, 50-70 µs carrier CPU per round trip | many |

Consequences for the design:

- The in-kernel GIC (`hv_gic`) is required: with it, the virtual timer, SGIs
  and WFI all stay inside the hypervisor with no exit to Carrick. It must be
  created before any vCPU, and each vCPU needs a unique MPIDR before its
  redistributor is touched. `applevisor-sys` 1.0.0 swaps its IRQ/FIQ enum
  values; any adoption must correct the binding.
- Switching guest threads on a running vCPU is 3 orders of magnitude cheaper
  than today's futex round trip. The expensive event is waking a PARKED vCPU
  (about 6 µs, host thread wakeup), so the scheduler should keep vCPUs that
  have imminent work running, and park only when idle for longer than the
  wake cost.
- vCPU threads need a latency-sensitive host thread policy: at default QoS a
  parked vCPU's timer wake is late by about 26% of the requested delay
  (258 µs for a 1 ms sleep); a time-constraint policy brings it to about 5 µs.
- Not yet working in the spike: `hv_gic_set_spi` never reached the CPU
  interface (likely setup), and one of three `hv_vcpus_exit` wake runs
  wedged. Neither is needed if SGIs carry cross-vCPU wakes, but both must be
  understood before acceptance.

A separate finding for today's runtime: the futex ping-pong costs 26-31 µs
with the default executor configuration but about 3 µs with
`CARRICK_BOUND_EXECUTORS=2`; the default placement is worth investigating now,
independently of this design.

## Memory

- **Frame pool.** The host grants stage-2-backed frames in large extents
  (hv_vm_map once per extent); EL1 runs the page allocator. EL1 returns free
  extents on a watermark (a hypercall; the host unmaps and madvise-frees them),
  so guest RAM tracks use, not a reservation.
- **Stage-1 is EL1's.** EL1 builds and edits every address space's tables,
  services first-touch, permission and COW faults, and invalidates with
  broadcast TLBI (range TLBI for munmap). Full break-before-make; software
  access and dirty tracking (HVF exposes no hardware A/D management).
- **Fork** copies page tables and write-protects in EL1; COW faults resolve in
  EL1. The host is not involved.
- **Zeroing.** A frame handed out for anonymous memory is zeroed by EL1 unless
  its provenance proves it zero (fresh host grant).
- **File-backed private mappings** fill from the EL1 page cache.
- **Shared mappings of host files** that host processes may also map keep a
  host-backed stage-2 alias; EL1 maps it but does not own its bytes.
- **Invariants carried over** from AGENTS.md: guest VA, stage-1 IPA and frame
  identity stay distinct typed domains; publication is transactional;
  coalescing requires alignment.

Measured (many-address-space spike, `spike/el1-asid` `25f6e2f4e`, same host;
every result has a negative control that fails as expected):

- **ASIDs isolate address spaces** at 2 to 4096 address spaces with no flush on
  switch (16-bit ASIDs are real on HVF). Switch plus one read: 15 ns at 2
  address spaces, 148 ns at 4096; a flush-on-switch instead costs 310-400 ns.
- **ASID-scoped invalidation is scoped:** `ASIDE1IS`/`VAE1IS` for one ASID
  leave other ASIDs' translations cached.
- **munmap must use range TLBI.** `RVAE1IS` costs 125-292 ns p50 at every size
  up to 4096 pages; a per-page `VAE1IS` loop costs about 73 ns per page (276-380
  µs at 4096). Minimum range is 2 pages.
- **ASID rollover** with a generation allocator and `VMALLE1IS` is correct
  (0 leaks over about 880k rollovers); the switch fast path must be lock-free
  (the spike's global lock cost 250-1300 ns under contention).
- **Interrupts during page-table edits are safe** with two rules: an EL1
  handler saves ELR/SPSR before anything that can fault, and IRQ handlers never
  take the page-table lock (mask IRQs across the short break-before-make
  section, about 170-250 ns, or defer).
- **Fork-style COW in EL1 is correct** across 4-8 vCPUs; a COW fault costs
  about 400-700 ns p50 (about 2x a zero-fill fault), against about 1 µs for a
  host-resolved fault before any pause.
- Not explained: occasional VM-wide TLB losses (performance only; suspected
  host stage-2 activity), and one wedged vCPU with the GIC active that ignored
  `hv_vcpus_exit`; recovery of a wedged vCPU under the GIC is not established.

## Files and the VFS

- EL1 owns the fd table, open file descriptions, the dentry cache and a page
  cache. Reads and writes of cached pages never exit; misses and write-back
  are file-bytes requests.
- Namespace mutations (rename, unlink, mkdir, link) are one namespace request
  each; EL1 updates its dentry cache from the completion. The per-call host
  cost of these (50-260 µs today) is stage 2a work that remains necessary in
  this design.
- Host writers outside Carrick: EL1's page cache must revalidate against host
  change (mtime/size/generation on open and on a bounded cadence), as the
  current file zone must.

## One kernel, every backend

Size is not the obstacle: `no_std` + `alloc` keeps `Vec`, `BTreeMap`, `Arc`
and atomics, so pure logic ports almost for free. What costs is coupling:
host-crossing calls (`libc::`, `std::fs/net/process/os`, host fds), which must
become hypercalls, and host-thread blocking (condvars, `parking_lot`), which
must become EL1 scheduler waits. Measured per file on `carrick-kernel`
(2026-09-24, coarse: one call marks a file): 8% of lines are in files with
neither, 5% blocking only, 22% host I/O only, 65% both. By density the object
graph (`kernel/`, about 79k lines, about 350 host references) is mostly logic
behind a thin boundary; `dispatch/fs` (about 1,000 in 36k lines) and
`dispatch/net` (about 1,300 in 21k) are boundary code that becomes hypercall
clients rather than being ported. So a wholesale port is a restructuring, not
a translation, and is not a plan. The pattern already in the tree
is: a platform-neutral `no_std` core per subsystem (as `carrick-inotify-core`,
`carrick-signal-core`, `carrick-timer-core`), executed at EL1 on HVF and, until
the other backends run a guest-privileged kernel, in-process on the host by
those backends. One implementation, two venues; the host-side venue is a thin
adapter, never a second implementation.

- HVF aarch64 runs the cores at EL1.
- KVM, bhyve and NVMM run the same cores in-process until the x86 ring-0 venue
  exists; the x86 engine (`carrick-x86`) is the place that venue lands.
- The shared cores are what `just test-kernel` exercises VM-free.

## Migration order

Each step lands with a red-first contract, a census before and after, and the
deletion of the host implementation it replaces (no parallel path, `=0` hatch
only for bisection).

0. Memory-bookkeeping algorithms (in progress; independent of this design).
1. Scheduler, futex and in-guest context switch, with parked-vCPU wake.
   Target: the 24% executor sleep/wake share on go build.
2. Anonymous memory, faults, brk/mmap/munmap and the frame pool. Target: the
   fault and mm-syscall shares; deletes the host page-table pause.
3. fd tables, pipes, AF_UNIX, eventfd, epoll over in-zone objects, signals.
4. Dentry/stat cache and name resolution; page cache for host files (subsumes
   the current file zone).
5. fork/exec in EL1.
6. x86 ring-0 venue for the other backends.

## Risks

- **Scale.** Steps 1-2 alone touch the executor, the scheduler, the mm
  authority and fork. The pause-timeout fix now in progress touches 16 files;
  this is larger.
- **Security.** Guest EL0 is isolated from EL1 by hardware, but EL1 code is
  reachable by guest syscalls. Host resources stay protected only by host-side
  validation of every hypercall. There has been no adversarial review, and
  this design does not change the status statement.
- **Debuggability.** DTrace and lldb do not see EL1. The design needs an
  in-guest event ring and counters exported through shared memory (the EL1
  counters and census are the start), readable live and from a core.
- **Premise drift.** A frame pool and an in-guest scheduler edge toward "a
  guest kernel with its own RAM". Elastic return and host-scheduled vCPUs are
  requirements, not optimizations; each needs a contract.
- **HVF behaviour not yet verified:** interrupt delivery for cross-vCPU wake
  and virtual-timer preemption at EL1; ASID-scoped invalidation across many
  address spaces; timer interrupts during page-table edits.

## 1b: in-guest futex handoff (as built)

Increment 1b moves one scheduling decision into the guest: when a thread of a
process wakes a sibling through a private futex and then waits, EL1 switches
the vCPU to the woken thread with no host exit and no host condvar. Signals,
exit, exec, timeouts and every other futex shape stay on the host. The host
and EL1 share one set of wait queues, so each case has one path.

### Ownership

The shared objects live in `carrick-sched-core`, a `no_std` crate compiled into
both the EL1 image and the host. They sit in the EL1 region at
`EL1_ZONE_OFFSET` (0x350_0000, 11 MiB reserved):

- A **zone record** (4096) per parked thread. It holds the thread's full EL0
  context (`ThreadCtx`: x0-x30, pc, pstate, `SP_EL0`, `TPIDR_EL0`,
  `TPIDRRO_EL0`, `CONTEXTIDR_EL1`, v0-v31, FPSR, FPCR) and one 64-bit claim
  word.
- **Wait queues**: 1024 hash buckets keyed by (address-space id, futex
  address), with 8192 queue entries. A bucket lock is a spin word; EL1 spins a
  bounded number of times and then forwards, while the host spins and yields.
- A **run queue** per EL1 mailbox slot, holding up to 8 woken threads, plus the
  slot's `current` and `host_record` fields.

The claim word names the one owner of a record at every instant:

| Claim | Owner | Who may move it |
|---|---|---|
| `Parked{seq}` | nobody; the record is on wait queues | any waker, the host for a signal, timeout or teardown; one CAS wins |
| `Queued{slot,seq}` / `OnCpu{slot,seq}` | slot `slot`: EL1 while its vCPU runs, the executor holding the slot while it is stopped at an exit | only that slot; the host reaches it by kicking the slot |
| `Host{seq}` | the host; the context is frozen until the thread is loaded | the host job that loads it, which frees the record |

The owner is a type, not a convention. The functions that move a record take
the claim they require (a `BucketGuard`, a `SlotId`, a `RecordRef` whose
incarnation must still match), and the context is reachable only through a
claim that grants it. `ThreadIdentity` (tid, thread serial, address-space id,
file table, generation) names the exact kernel thread, so a record never
outlives or crosses to another incarnation.

On the host, a zone-parked thread is an ordinary blocked continuation
(`BlockedContinuation::ZoneFutexWait`, family `zone-futex-wait`). It owns a
`ZoneWait` whose `Drop` cancels the record: an unconsumed wait frees its record
or flags it for cancellation. Its CPU residency is
`TaskCpuResidency::Zone{base, record}`: loading it materializes the host-held
base state overlaid with the record's context.

### What EL1 serves

EL1 serves only these operations, for a process whose zone key is published on
the slot (`CurrentTask::zone_mm`, non-zero):

- `FUTEX_WAKE_PRIVATE` / `FUTEX_WAKE_BITSET_PRIVATE` with a positive count and
  a non-zero bitset. EL1 claims matching `Parked` waiters onto its own slot's
  run queue (`Queued`) and returns the count. It never runs a woken thread
  from the wake. The wake is all or nothing: if it would wake more waiters
  than the run queue has free entries (at most 8), EL1 forwards the whole
  wake. An early build capped the count instead, so `FUTEX_WAKE(9)` woke 8
  (`futexforkwakegroups`).
- Untimed `FUTEX_WAIT_PRIVATE` / `FUTEX_WAIT_BITSET_PRIVATE`, and only when a
  woken thread is queued on this slot. EL1 checks the futex word under the
  bucket lock (EAGAIN if it differs), saves the caller's context into a fresh
  record, publishes it `Parked`, and switches in the oldest queued thread with
  x0 set to its result (`OnCpu`). FP/SIMD moves through the audited
  `carrick_el1_fpsimd_save`/`_load` routines (the image checker allow-lists
  exactly those FP instructions).

Everything else is forwarded. That covers timeouts, requeue, `futex_waitv`,
shared futexes, PI futexes, `FUTEX_CLOCK_REALTIME`, a zero or negative count,
bitset 0, a busy bucket lock, a wake larger than the run queue's free space, a
waiter parked on several futexes (`futex_waitv`), a fault on the futex word, and
a wait with no queued successor. While threads are queued on the slot, any
other syscall is also forwarded, and so is any syscall while host work is
pending. The host services a zone process's private futex operations on the
same queues through the same core functions: a host wait parks the thread in
the zone (writing the record's context from the exit), and host wakes, requeue
and the `CLONE_CHILD_CLEARTID` exit wake use the zone's wake. `futex_waitv`
parks only on its last entry, matching Carrick's existing `FutexTable`
behaviour. PI futexes and `MAP_SHARED` futexes stay on their existing paths.

### How the host reaches a thread parked in EL1

At every guest exit of a slot, except a stage-1 COW fault, which resumes
without a thread boundary, the executor **reconciles** the slot:

1. Every woken record still queued on the slot is handed back to the host
   (`Host`, handback `Woken`) and its thread is made runnable.
2. If EL1 switched the vCPU to another thread, the record now running
   (`OnCpu`) receives the vCPU's live EL0 context. A syscall exit is rewound
   one instruction unless the syscall was served. The record is handed back as
   `Resumed`, and the thread the host had loaded settles into a zone wait on
   the record EL1 parked it in. If the running record is the loaded thread's
   own, it is simply released.

The host's other reach is the claim. A signal, a timeout or a control action
(exit, exec drain, teardown) must first win the record's claim before it acts:

- `CarrierWaitService::publish_event` admits a zone wait's event only after
  winning the claim.
- `scheduler_control_wake` refuses a record EL1 holds (the slot is kicked
  instead).
- The executor's settle claims a pending control action.
- A timeout claims only the park whose sequence number armed it, so a stale
  deadline cannot claim a later park.

A record EL1 holds is reached by kicking its slot. The exit reconciles it, and
the claim then succeeds on the host-owned record.

A thread loaded from a handback runs the `ResumeZone` phase. The phase applies
the handback: `Woken` returns the wake result, `Resumed` leaves the registers
as they are, `Timeout` returns ETIMEDOUT and `Signal` returns EINTR. It then
frees the record and delivers pending signals at that EL0 boundary. So:

- A **signal** to a zone-parked thread claims the record (`Signal`), the thread
  resumes with EINTR, and its handler runs.
- **exit_group** and **execve** claim or kick every parked sibling (`Control`);
  each is loaded and retired or drained on the host exactly as a host-parked
  thread is.
- **fork** copies only the calling thread. The child is a new address space,
  so its futexes have a new zone key. Siblings EL1 holds are handed back by the
  fork quiesce's kicks.
- **ptrace** of another thread is not supported by Carrick (Phase 1 only); the
  zone adds nothing there.

A run-queue guard thread checks every 2 ms and kicks a slot whose run queue
has stayed non-empty since the same instant. This keeps a woken thread from
starving behind a running thread that neither blocks nor makes a syscall. It
is a poll. EL1 timer preemption (the 1a GIC path) should replace it once EL1
takes the timer at EL0.

`CARRICK_EL1_FUTEX=0` (exact) turns the zone off: EL1 forwards every futex
operation and the host uses the pre-1b paths.

### Deliberate divergences and limits

- A signal ends a zone wait with EINTR even with `SA_RESTART`, the same as the
  host path today (futex waits are restart class `Never` in Carrick). Linux
  restarts an untimed `FUTEX_WAIT` for `SA_RESTART` handlers.
- A control handback (`Control`) that does not retire the thread returns 0, a
  spurious wake, which futex callers must tolerate.
- Record or entry exhaustion (4096 / 8192) makes a wait return EAGAIN, which
  callers retry. The capacity is fixed.
- A woken thread waits on the waker's slot. It runs when the waker blocks in a
  served wait, when the waker makes any other syscall, or within about 2 ms
  (the guard).
- `futex_waitv` parks only on its last entry (existing Carrick behaviour).

### Measured

Measured on Apple M4, macOS 27.2, 2026-09-25 (signed
`el1_sched_futex_handoff_has_no_host_exits`). The fixture runs two threads
ping-ponging through `FUTEX_WAIT_PRIVATE`/`FUTEX_WAKE_PRIVATE`. The per
round-trip cost is the difference between 55k and 5k round-trip runs, so
startup and teardown cancel:

| | main 612532918 | 1b |
|---|---|---|
| host exits per round trip | 5.34, 5.43 | 0.0019, 0.0020 |
| carrier CPU per round trip | 93, 95 µs | 0.67, 0.77 µs |
| round-trip latency p50 | 48 µs | 0.54-0.58 µs |

With `CARRICK_EL1_FUTEX=0` the same binary gives a 2.8 µs p50 round trip (CLI,
20k iterations). The remaining exits (about one per 500 round trips) are host
preemption kicks and the guard. On the zone-readers fixture (4 processes x 8
threads reading files), one attempt took 9.1-9.7 s with the zone and 18.8-20.8 s
with the hatch or on main. That suggests a real workload gain, but it is not a
controlled single-variable measurement.

On `go build` (the `go-build` suite command, `--fs host`, three interleaved
runs per arm on one quiet host), total CPU (user+sys) was 3.42-3.51 s on main,
3.34-3.44 s with 1b, and 3.52-3.64 s with the hatch, at 1.37-1.44 s wall for
every arm. That suggests little change: this build spends few of its
host round trips on handoffs between sibling threads, and the executor
sleep/wake share named under Migration order is not yet addressed by 1b alone.

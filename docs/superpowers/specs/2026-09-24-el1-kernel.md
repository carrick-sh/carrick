# The EL1 kernel: Carrick's kernel runs in the guest, the host is the platform

Status: ACCEPTED by the owner, 2026-09-24. Carrick's direction is an EL1
kernel. This supersedes stages 2-4 of
[`2026-09-24-zone-the-workloads.md`](2026-09-24-zone-the-workloads.md); stage 1
(the file zone) and the memory-bookkeeping fixes stand. Acceptance commits to
the direction and the migration order, not to every detail below: each
increment still lands only with its red-first contracts, census and signed
gates, and the open items under "Before acceptance" are now entry criteria for
the increments that depend on them.

## Decision requested

Stop moving objects into EL1 one at a time with no end state. Adopt an end
state in which Carrick's kernel executes at guest EL1 and owns every object
that never leaves the Linux compat zone, and the host process is a platform:
vCPUs, bulk memory, host files, host sockets, clocks. Migrate to it subsystem
by subsystem, deleting each host implementation as its EL1 replacement lands.

## Evidence

All measured on Apple M4, macOS 27, signed builds of local main. Single runs
unless stated; "suggests" where the method is not a controlled experiment.

| Finding | Evidence |
|---|---|
| Two owners per object is where the defects are | This campaign's defects were coherence between host and EL1 or host-process-shaped authority: delegate/recall (abandoned), lazy member detach, the mailbox-slot cache that served one process's files to another (`fd11bd8cc`), the discard/COW shadowed-row lookup |
| Moving single objects wins locally, not on workloads | inotify09 2.7 s vs 36 s with EL1 off; the ecosystem census shows the zone's classes are a small share of host syscall CPU ([census](../../perf-results/2026-09-24-el1-census.md)) |
| Exits themselves are small | VM exit/entry plus register sync: about 6% of carrier CPU on both go build and cpython (profile, below) |
| Host thread scheduling is large on Go | go build (hello, cold cache): executor block/wake, condvar and scheduler locks = about 24% of carrier CPU; guest execution 31% |
| Memory bookkeeping is large on Python | cpython tests: fault/COW service 26% and mm syscalls 14% of carrier CPU, mostly Carrick user-space index walks (being fixed now, independent of this design) |
| Guest EL1 can own stage-1 | spike `spike/el1-tlbi-stage1` `18ffa1c51`: broadcast TLBI invalidates sibling vCPUs with no host action (0 stale of 370M reads at 8 vCPUs; control without TLBI: 91% stale); EL0 translation faults are taken at guest EL1 with no exit |
| In-guest fault service is cheaper and removes the pause | first-touch fault in EL1 190-250 ns vs 0.9-1.3 µs host-resolved without any pause; host pause of 8 vCPUs p99 0.3-1.6 ms (tail up to 3.3 ms), the mechanism behind the `fault page-table pause ... TimedOut` guest crashes |

Profile method: `profile-997` on the carrier, samples split into guest
execution (the qualified HVF guest PC), host kernel and user, user stacks
symbolized offline and bucketed by frame. Scripts are scratch today and become
a `carrick trace` profile before this design is accepted (Rust-first rule).

## Goal and the premise it must keep

Goal: correctness by construction (one owner, one implementation per object)
and host-native cost: within 2x of native-arm64 Docker per row, no
load-dependent verdicts.

Carrick's premise constrains the design. It must keep:

- **Host scheduling of CPU.** vCPUs are host threads the host schedules; an
  idle vCPU costs nothing. No fixed guest CPU reservation.
- **Elastic memory.** The host grants frames on demand and the guest returns
  free frames promptly. No fixed-size VM RAM pool sized up front.
- **Host-native I/O.** Files are host files (bytes on APFS), sockets are host
  sockets, clocks are host clocks.
- **Honest status.** An EL1 kernel is guest-reachable privileged code; this
  design does not make a guest a hardened trust boundary (see Security).

## The host interface

One narrow hypercall ABI (HVC with a request ring in shared memory), versioned
by the existing ABI layout hash.

- **Classes:** file-bytes (read/write/fsync by host handle and offset),
  namespace (open/stat/rename/unlink/mkdir/link/xattr by contained parent
  handle and leaf), socket, memory (grant/reclaim frame extents), clock
  calibration, vCPU (park/wake), process-boundary (core file, exit status to
  the CLI).
- **Asynchronous by default.** A host request does not hold the vCPU: EL1
  queues it, switches to another runnable guest thread, and resumes the waiter
  on completion. This is what the current continuation machinery does in the
  host; in the end state it is EL1's ordinary blocking.
- **Batched.** Requests and completions travel in rings; one exit can carry
  many requests, and a busy vCPU need not exit to learn of completions.
- **Validated.** The host treats every request as untrusted input (guest EL1
  is guest-reachable). Path containment, handle ownership and quotas are
  enforced host-side, as the host backends enforce them today.

## Scheduling

- Each vCPU runs an EL1 scheduler over the runnable guest threads it owns; a
  context switch is register save/restore and a TTBR/ASID switch at EL1, not a
  host condvar.
- Preemption uses the guest virtual timer (CNTV) delivered at EL1.
- A vCPU with nothing runnable parks in the host (WFI or HVC exit); the host
  thread sleeps. Waking a parked vCPU is the only host involvement in guest
  scheduling.
- Load balancing across vCPUs is EL1's (work stealing between per-vCPU run
  queues); the host's scheduler still decides which vCPU threads run.
- The vCPU count stays elastic: the host adds vCPUs up to the core count and
  retires idle ones.

Measured (scheduler spike, `spike/el1-scheduler` `c9897ae4c`, Apple M4,
macOS 27.2, shared host at load 3-6):

| Operation | Cost | Host exits |
|---|---|---|
| EL1 thread switch, same address space | 28 ns p50 | 0 |
| EL1 switch, other address space (ASID, no flush) | 42 ns; 54 ns with FP/SIMD | 0 |
| Switch with a TLB flush (the control) | 190-440 ns | 0 |
| Timer preemption via `hv_gic` (vtimer PPI 27 at EL1) | deadline to handler under 42 ns p50 | 0 |
| Timer preemption without the GIC | 1.0-1.5 µs p50 | 2 per tick |
| Wake a vCPU parked in WFI, by SGI | 6-10 µs p50 (4 µs with a time-constraint thread policy) | 0 to our process |
| Wake a running vCPU, by SGI | 1.8-2.0 µs p50 | 0 to our process |
| Today: host condvar round trip | 2.3 µs p50 | n/a |
| Today: guest futex ping-pong under Carrick | 26-31 µs mean, 50-70 µs carrier CPU per round trip | many |

Consequences for the design:

- The in-kernel GIC (`hv_gic`) is required: with it, the virtual timer, SGIs
  and WFI all stay inside the hypervisor with no exit to Carrick. It must be
  created before any vCPU, and each vCPU needs a unique MPIDR before its
  redistributor is touched. `applevisor-sys` 1.0.0 swaps its IRQ/FIQ enum
  values; any adoption must correct the binding.
- Switching guest threads on a running vCPU is 3 orders of magnitude cheaper
  than today's futex round trip. The expensive event is waking a PARKED vCPU
  (about 6 µs, host thread wakeup), so the scheduler should keep vCPUs that
  have imminent work running, and park only when idle for longer than the
  wake cost.
- vCPU threads need a latency-sensitive host thread policy: at default QoS a
  parked vCPU's timer wake is late by about 26% of the requested delay
  (258 µs for a 1 ms sleep); a time-constraint policy brings it to about 5 µs.
- Not yet working in the spike: `hv_gic_set_spi` never reached the CPU
  interface (likely setup), and one of three `hv_vcpus_exit` wake runs
  wedged. Neither is needed if SGIs carry cross-vCPU wakes, but both must be
  understood before acceptance.

A separate finding for today's runtime: the futex ping-pong costs 26-31 µs
with the default executor configuration but about 3 µs with
`CARRICK_BOUND_EXECUTORS=2`; the default placement is worth investigating now,
independently of this design.

## Memory

- **Frame pool.** The host grants stage-2-backed frames in large extents
  (hv_vm_map once per extent); EL1 runs the page allocator. EL1 returns free
  extents on a watermark (a hypercall; the host unmaps and madvise-frees them),
  so guest RAM tracks use, not a reservation.
- **Stage-1 is EL1's.** EL1 builds and edits every address space's tables,
  services first-touch, permission and COW faults, and invalidates with
  broadcast TLBI (range TLBI for munmap). Full break-before-make; software
  access and dirty tracking (HVF exposes no hardware A/D management).
- **Fork** copies page tables and write-protects in EL1; COW faults resolve in
  EL1. The host is not involved.
- **Zeroing.** A frame handed out for anonymous memory is zeroed by EL1 unless
  its provenance proves it zero (fresh host grant).
- **File-backed private mappings** fill from the EL1 page cache.
- **Shared mappings of host files** that host processes may also map keep a
  host-backed stage-2 alias; EL1 maps it but does not own its bytes.
- **Invariants carried over** from AGENTS.md: guest VA, stage-1 IPA and frame
  identity stay distinct typed domains; publication is transactional;
  coalescing requires alignment.

Measured (many-address-space spike, `spike/el1-asid` `25f6e2f4e`, same host;
every result has a negative control that fails as expected):

- **ASIDs isolate address spaces** at 2 to 4096 address spaces with no flush on
  switch (16-bit ASIDs are real on HVF). Switch plus one read: 15 ns at 2
  address spaces, 148 ns at 4096; a flush-on-switch instead costs 310-400 ns.
- **ASID-scoped invalidation is scoped:** `ASIDE1IS`/`VAE1IS` for one ASID
  leave other ASIDs' translations cached.
- **munmap must use range TLBI.** `RVAE1IS` costs 125-292 ns p50 at every size
  up to 4096 pages; a per-page `VAE1IS` loop costs about 73 ns per page (276-380
  µs at 4096). Minimum range is 2 pages.
- **ASID rollover** with a generation allocator and `VMALLE1IS` is correct
  (0 leaks over about 880k rollovers); the switch fast path must be lock-free
  (the spike's global lock cost 250-1300 ns under contention).
- **Interrupts during page-table edits are safe** with two rules: an EL1
  handler saves ELR/SPSR before anything that can fault, and IRQ handlers never
  take the page-table lock (mask IRQs across the short break-before-make
  section, about 170-250 ns, or defer).
- **Fork-style COW in EL1 is correct** across 4-8 vCPUs; a COW fault costs
  about 400-700 ns p50 (about 2x a zero-fill fault), against about 1 µs for a
  host-resolved fault before any pause.
- Not explained: occasional VM-wide TLB losses (performance only; suspected
  host stage-2 activity), and one wedged vCPU with the GIC active that ignored
  `hv_vcpus_exit`; recovery of a wedged vCPU under the GIC is not established.

## Files and the VFS

- EL1 owns the fd table, open file descriptions, the dentry cache and a page
  cache. Reads and writes of cached pages never exit; misses and write-back
  are file-bytes requests.
- Namespace mutations (rename, unlink, mkdir, link) are one namespace request
  each; EL1 updates its dentry cache from the completion. The per-call host
  cost of these (50-260 µs today) is stage 2a work that remains necessary in
  this design.
- Host writers outside Carrick: EL1's page cache must revalidate against host
  change (mtime/size/generation on open and on a bounded cadence), as the
  current file zone must.

## One kernel, every backend

Size is not the obstacle: `no_std` + `alloc` keeps `Vec`, `BTreeMap`, `Arc`
and atomics, so pure logic ports almost for free. What costs is coupling:
host-crossing calls (`libc::`, `std::fs/net/process/os`, host fds), which must
become hypercalls, and host-thread blocking (condvars, `parking_lot`), which
must become EL1 scheduler waits. Measured per file on `carrick-kernel`
(2026-09-24, coarse: one call marks a file): 8% of lines are in files with
neither, 5% blocking only, 22% host I/O only, 65% both. By density the object
graph (`kernel/`, about 79k lines, about 350 host references) is mostly logic
behind a thin boundary; `dispatch/fs` (about 1,000 in 36k lines) and
`dispatch/net` (about 1,300 in 21k) are boundary code that becomes hypercall
clients rather than being ported. So a wholesale port is a restructuring, not
a translation, and is not a plan. The pattern already in the tree
is: a platform-neutral `no_std` core per subsystem (as `carrick-inotify-core`,
`carrick-signal-core`, `carrick-timer-core`), executed at EL1 on HVF and, until
the other backends run a guest-privileged kernel, in-process on the host by
those backends. One implementation, two venues; the host-side venue is a thin
adapter, never a second implementation.

- HVF aarch64 runs the cores at EL1.
- KVM, bhyve and NVMM run the same cores in-process until the x86 ring-0 venue
  exists; the x86 engine (`carrick-x86`) is the place that venue lands.
- The shared cores are what `just test-kernel` exercises VM-free.

## Migration order

Each step lands with a red-first contract, a census before and after, and the
deletion of the host implementation it replaces (no parallel path, `=0` hatch
only for bisection).

0. Memory-bookkeeping algorithms (in progress; independent of this design).
1. Scheduler, futex and in-guest context switch, with parked-vCPU wake.
   Target: the 24% executor sleep/wake share on go build.
2. Anonymous memory, faults, brk/mmap/munmap and the frame pool. Target: the
   fault and mm-syscall shares; deletes the host page-table pause.
3. fd tables, pipes, AF_UNIX, eventfd, epoll over in-zone objects, signals.
4. Dentry/stat cache and name resolution; page cache for host files (subsumes
   the current file zone).
5. fork/exec in EL1.
6. x86 ring-0 venue for the other backends.

## Risks

- **Scale.** Steps 1-2 alone touch the executor, the scheduler, the mm
  authority and fork. The pause-timeout fix now in progress touches 16 files;
  this is larger.
- **Security.** Guest EL0 is isolated from EL1 by hardware, but EL1 code is
  reachable by guest syscalls. Host resources stay protected only by host-side
  validation of every hypercall. There has been no adversarial review, and
  this design does not change the status statement.
- **Debuggability.** DTrace and lldb do not see EL1. The design needs an
  in-guest event ring and counters exported through shared memory (the EL1
  counters and census are the start), readable live and from a core.
- **Premise drift.** A frame pool and an in-guest scheduler edge toward "a
  guest kernel with its own RAM". Elastic return and host-scheduled vCPUs are
  requirements, not optimizations; each needs a contract.
- **HVF behaviour not yet verified:** interrupt delivery for cross-vCPU wake
  and virtual-timer preemption at EL1; ASID-scoped invalidation across many
  address spaces; timer interrupts during page-table edits.

## 1b: in-guest futex handoff (as built)

Increment 1b moves one scheduling decision into the guest: when a thread of a
process wakes a sibling through a private futex and then waits, EL1 switches
the vCPU to the woken thread with no host exit and no host condvar. Signals,
exit, exec, timeouts and every other futex shape stay on the host. The host
and EL1 share one set of wait queues, so each case has one path.

### Ownership

The shared objects live in `carrick-sched-core`, a `no_std` crate compiled into
both the EL1 image and the host. They sit in the EL1 region at
`EL1_ZONE_OFFSET` (0x350_0000, 11 MiB reserved):

- A **zone record** (4096) per parked thread. It holds the thread's full EL0
  context (`ThreadCtx`: x0-x30, pc, pstate, `SP_EL0`, `TPIDR_EL0`,
  `TPIDRRO_EL0`, `CONTEXTIDR_EL1`, v0-v31, FPSR, FPCR) and one 64-bit claim
  word.
- **Wait queues**: 1024 hash buckets keyed by (address-space id, futex
  address), with 8192 queue entries. A bucket lock is a spin word; EL1 spins a
  bounded number of times and then forwards, while the host spins and yields.
- A **run queue** per EL1 mailbox slot, holding up to 8 woken threads, plus the
  slot's `current` and `host_record` fields.

The claim word names the one owner of a record at every instant:

| Claim | Owner | Who may move it |
|---|---|---|
| `Parked{seq}` | nobody; the record is on wait queues | any waker, the host for a signal, timeout or teardown; one CAS wins |
| `Queued{slot,seq}` / `OnCpu{slot,seq}` | slot `slot`: EL1 while its vCPU runs, the executor holding the slot while it is stopped at an exit | only that slot; the host reaches it by kicking the slot |
| `Host{seq}` | the host; the context is frozen until the thread is loaded | the host job that loads it, which frees the record |

The owner is a type, not a convention. The functions that move a record take
the claim they require (a `BucketGuard`, a `SlotId`, a `RecordRef` whose
incarnation must still match), and the context is reachable only through a
claim that grants it. `ThreadIdentity` (tid, thread serial, address-space id,
file table, generation) names the exact kernel thread, so a record never
outlives or crosses to another incarnation.

On the host, a zone-parked thread is an ordinary blocked continuation
(`BlockedContinuation::ZoneFutexWait`, family `zone-futex-wait`). It owns a
`ZoneWait` whose `Drop` cancels the record: an unconsumed wait frees its record
or flags it for cancellation. Its CPU residency is
`TaskCpuResidency::Zone{base, record}`: loading it materializes the host-held
base state overlaid with the record's context.

### What EL1 serves

EL1 serves only these operations, for a process whose zone key is published on
the slot (`CurrentTask::zone_mm`, non-zero):

- `FUTEX_WAKE_PRIVATE` / `FUTEX_WAKE_BITSET_PRIVATE` with a positive count and
  a non-zero bitset. EL1 claims matching `Parked` waiters onto its own slot's
  run queue (`Queued`) and returns the count. It never runs a woken thread
  from the wake. The wake is all or nothing: if it would wake more waiters
  than the run queue has free entries (at most 8), EL1 forwards the whole
  wake. An early build capped the count instead, so `FUTEX_WAKE(9)` woke 8
  (`futexforkwakegroups`).
- Untimed `FUTEX_WAIT_PRIVATE` / `FUTEX_WAIT_BITSET_PRIVATE`, and only when a
  woken thread is queued on this slot. EL1 checks the futex word under the
  bucket lock (EAGAIN if it differs), saves the caller's context into a fresh
  record, publishes it `Parked`, and switches in the oldest queued thread with
  x0 set to its result (`OnCpu`). FP/SIMD moves through the audited
  `carrick_el1_fpsimd_save`/`_load` routines (the image checker allow-lists
  exactly those FP instructions).

Everything else is forwarded. That covers timeouts, requeue, `futex_waitv`,
shared futexes, PI futexes, `FUTEX_CLOCK_REALTIME`, a zero or negative count,
bitset 0, a busy bucket lock, a wake larger than the run queue's free space, a
waiter parked on several futexes (`futex_waitv`), a fault on the futex word, and
a wait with no queued successor. While threads are queued on the slot, any
other syscall is also forwarded, and so is any syscall while host work is
pending. The host services a zone process's private futex operations on the
same queues through the same core functions: a host wait parks the thread in
the zone (writing the record's context from the exit), and host wakes, requeue
and the `CLONE_CHILD_CLEARTID` exit wake use the zone's wake. `futex_waitv`
parks only on its last entry, matching Carrick's existing `FutexTable`
behaviour. PI futexes and `MAP_SHARED` futexes stay on their existing paths.

### How the host reaches a thread parked in EL1

At every guest exit of a slot, except a stage-1 COW fault, which resumes
without a thread boundary, the executor **reconciles** the slot:

1. Every woken record still queued on the slot is handed back to the host
   (`Host`, handback `Woken`) and its thread is made runnable.
2. If EL1 switched the vCPU to another thread, the record now running
   (`OnCpu`) receives the vCPU's live EL0 context. A syscall exit is rewound
   one instruction unless the syscall was served. The record is handed back as
   `Resumed`, and the thread the host had loaded settles into a zone wait on
   the record EL1 parked it in. If the running record is the loaded thread's
   own, it is simply released.

The host's other reach is the claim. A signal, a timeout or a control action
(exit, exec drain, teardown) must first win the record's claim before it acts:

- `CarrierWaitService::publish_event` admits a zone wait's event only after
  winning the claim.
- `scheduler_control_wake` refuses a record EL1 holds (the slot is kicked
  instead).
- The executor's settle claims a pending control action.
- A timeout claims only the park whose sequence number armed it, so a stale
  deadline cannot claim a later park.

A record EL1 holds is reached by kicking its slot. The exit reconciles it, and
the claim then succeeds on the host-owned record.

A thread loaded from a handback runs the `ResumeZone` phase. The phase applies
the handback: `Woken` returns the wake result, `Resumed` leaves the registers
as they are, `Timeout` returns ETIMEDOUT and `Signal` returns EINTR. It then
frees the record and delivers pending signals at that EL0 boundary. So:

- A **signal** to a zone-parked thread claims the record (`Signal`), the thread
  resumes with EINTR, and its handler runs.
- **exit_group** and **execve** claim or kick every parked sibling (`Control`);
  each is loaded and retired or drained on the host exactly as a host-parked
  thread is.
- **fork** copies only the calling thread. The child is a new address space,
  so its futexes have a new zone key. Siblings EL1 holds are handed back by the
  fork quiesce's kicks.
- **ptrace** of another thread is not supported by Carrick (Phase 1 only); the
  zone adds nothing there.

A run-queue guard thread checks every 2 ms and kicks a slot whose run queue
has stayed non-empty since the same instant. This keeps a woken thread from
starving behind a running thread that neither blocks nor makes a syscall. It
is a poll. EL1 timer preemption (the 1a GIC path) should replace it once EL1
takes the timer at EL0.

`CARRICK_EL1_FUTEX=0` (exact) turns the zone off: EL1 forwards every futex
operation and the host uses the pre-1b paths.

### Deliberate divergences and limits

- A signal ends a zone wait with EINTR even with `SA_RESTART`, the same as the
  host path today (futex waits are restart class `Never` in Carrick). Linux
  restarts an untimed `FUTEX_WAIT` for `SA_RESTART` handlers.
- A control handback (`Control`) that does not retire the thread returns 0, a
  spurious wake, which futex callers must tolerate.
- Record or entry exhaustion (4096 / 8192) makes a wait return EAGAIN, which
  callers retry. The capacity is fixed.
- A woken thread waits on the waker's slot. It runs when the waker blocks in a
  served wait, when the waker makes any other syscall, or within about 2 ms
  (the guard).
- `futex_waitv` parks only on its last entry (existing Carrick behaviour).

### Measured

Measured on Apple M4, macOS 27.2, 2026-09-25 (signed
`el1_sched_futex_handoff_has_no_host_exits`). The fixture runs two threads
ping-ponging through `FUTEX_WAIT_PRIVATE`/`FUTEX_WAKE_PRIVATE`. The per
round-trip cost is the difference between 55k and 5k round-trip runs, so
startup and teardown cancel:

| | main 612532918 | 1b |
|---|---|---|
| host exits per round trip | 5.34, 5.43 | 0.0019, 0.0020 |
| carrier CPU per round trip | 93, 95 µs | 0.67, 0.77 µs |
| round-trip latency p50 | 48 µs | 0.54-0.58 µs |

With `CARRICK_EL1_FUTEX=0` the same binary gives a 2.8 µs p50 round trip (CLI,
20k iterations). The remaining exits (about one per 500 round trips) are host
preemption kicks and the guard. On the zone-readers fixture (4 processes x 8
threads reading files), one attempt took 9.1-9.7 s with the zone and 18.8-20.8 s
with the hatch or on main. That suggests a real workload gain, but it is not a
controlled single-variable measurement.

On `go build` (the `go-build` suite command, `--fs host`, three interleaved
runs per arm on one quiet host), total CPU (user+sys) was 3.42-3.51 s on main,
3.34-3.44 s with 1b, and 3.52-3.64 s with the hatch, at 1.37-1.44 s wall for
every arm. That suggests little change: this build spends few of its
host round trips on handoffs between sibling threads, and the executor
sleep/wake share named under Migration order is not yet addressed by 1b alone.


## 1c: scheduling across vCPUs in the guest (as built)

Increment 1c makes the guest schedule threads across vCPUs. EL1 wakes a
thread onto another vCPU and signals it with an SGI, parks a vCPU with
nothing to run in WFI, ends a timed futex wait on the vCPU's virtual timer,
and preempts a thread that never makes a syscall. None of it exits to
Carrick: under Hypervisor.framework's in-kernel GIC the SGIs, the virtual
timer and WFI stay inside the hypervisor. The 2 ms run-queue guard of 1b is
deleted. Contract `kernel.el1.guest-scheduler`.

### Slots, their state and their lock

Each vCPU slot (the mailbox slot of an executor's vCPU) now has, in
`carrick-sched-core`:

- a run-queue lock (a spin word; EL1 spins a bounded number of times on
  another slot's lock and never holds two), and
- a `SlotState` other vCPUs read: `Host` (stopped at an exit, or never
  entered), `Running`, `IdleSpin` or `IdleWfi`.

EL1 may queue a thread on another slot only under that slot's lock and only
while the slot is in the guest. The executor marks the slot `Running` before
each `hv_vcpu_run` and sets `Host` under the same lock when the run returns,
before it drains the slot. So a thread is never queued on a slot nobody will
run. A VM-free test races cross-slot wakes against the exit transition 2,000
times and finds none stranded. Lock order: a futex bucket lock, then one slot
lock.

Other per-slot facts EL1 places threads by are published by the host at
load and at each entry: the address space installed on the vCPU, the guest
CPU its executor is bound to, and the loaded thread's affinity mask. EL1
publishes the slot's SGI routing (from `MPIDR_EL1`) before it idles.

### Home records

The record EL1 creates when the thread the host loaded on a slot parks or is
preempted is that slot's *home* record. The host still believes that thread
runs on that slot, so the record runs only there: a waker on another vCPU
queues it on its home slot (with an SGI if the home is running a thread or in
WFI) and refuses the wake (forwards it) while the home is stopped at an
exit. Switched back in, it simply becomes the running record again, as in
1b. When the executor settles the thread into a host zone wait at an exit,
the record stops being homed (`unhome`) and takes the thread's current
affinity; from then on it may run on any slot. This rule is what keeps the
host's view of which executor runs a thread true: a homed thread that ran on
another vCPU would leave its executor idling in the guest with nothing to
make it exit.

### Placement

A futex wake served in EL1 places each waiter:

1. a home record on its home slot;
2. otherwise the idle slot it last ran on, or any idle slot of the same
   address space whose guest CPU its affinity allows (the idle bitmap is a
   hint; the slot's lock and state decide);
3. otherwise the waker's own run queue, if its affinity allows the waker's
   CPU.

A waiter nothing can take refuses the whole wake, which the host serves (all
or nothing, as in 1b; the waker's own queue must still be able to take every
waiter). If the slot planned for a waiter changed between the plan and the
claim, the waiter goes to the waker's queue and, if it may not run there, the
waker leaves through the host (`ServedWithWork`), whose exit hands the thread
over; the zone counts these (`el1_misplaced`, zero in every run measured).

### Idle vCPUs

A futex wait with nothing runnable parks the thread (1b forwarded it) and
idles the vCPU in EL1, with IRQs masked:

- it polls its run queue for 20 us (`IDLE_SPIN_NS`, about twice the cost of
  waking a vCPU from WFI), in `IdleSpin`;
- then it parks in WFI (`IdleWfi`, decided under the slot lock, so a waker
  either sees `IdleWfi` and sends the SGI or its thread is seen first). WFI
  wakes on a pending interrupt even with IRQs masked; EL1 acknowledges by
  polling `ICC_IAR1_EL1` and completes each interrupt. A WFI may end early;
  the loop waits again.

The idle vCPU leaves the guest only for host work: the host kick SGI marks
it, and the idle loop returns `Action::Idle`, which the syscall hook turns
into the new `hvc #5` idle exit (SP_EL1 back on the mailbox, no thread on the
vCPU). The HVF run loop reports it as a halt. The executor's reconcile then
settles the parked thread from its record, exactly as for a thread EL1
parked while the vCPU ran another.

### Interrupts at EL0 and preemption

`El1IrqMode::Gic` changes the vector page:

- every served return to EL0 clears `I` in `SPSR_EL1`, so a pending timer or
  SGI is taken at the first EL0 instruction, including in a loop that never
  makes a syscall;
- the lower-EL IRQ slot enters an EL0 IRQ hook that saves the frame (syndrome
  0 marks it an interrupt) and calls the EL1 image; it leaves by `eret` or,
  when host work is pending, by the `hvc #4` kick exit at that EL0 boundary;
- EL1 never unmasks IRQs, so the current-EL IRQ slot fails loud (`hvc #3`).
  1a's served-path IRQ window and hand-encoded EL1 handler are gone.

The EL1 interrupt handler disarms and counts the virtual timer, ends this
slot's timed park if due, and, when a queued thread has waited a 2 ms slice
(`PREEMPT_SLICE_NS`), first moves queued non-home threads to idle slots and
then preempts the running thread into its record at the tail of the queue.
The kick SGI becomes pending host work and forwards. The timer is armed
lazily: only when EL1 needs an earlier interrupt than the one already armed;
a timer left armed fires once, finds nothing, and is disarmed.

The guest never sees the unmask. Every EL0 PSTATE it can read (a signal
frame's `pstate`, a core file's `pstate`) passes through
`el0_visible_pstate`, which shows DAIF as `0x3c0`, as Carrick has always run
EL0; `rt_sigreturn` restores what the frame says. The signed `pstate` test
reads `0x3c0` for a signal at a syscall boundary and for one interrupting a
loop after in-guest futex service (it was `0x340` without the
normalization).

### Timed waits

`FUTEX_WAIT_PRIVATE` with a relative timeout is served for the thread the
host loaded on the vCPU (a switched-in thread's timed wait forwards: its
deadline would outlive the vCPU's hold on it). The park records a CNTVCT
deadline and arms the slot's timer; at the deadline EL1 claims the park with
`ETIMEDOUT` onto its own run queue and switches it in. At an exit, the
executor gives a pending deadline to the host continuation (guest CNTVCT is
the host's `mach_absolute_time`), with the park's sequence number, so a
stale deadline cannot end a later park. Absolute and `FUTEX_CLOCK_REALTIME`
timeouts still forward.

### How the host reaches a thread parked on a WFI-parked vCPU

The host still believes a homed thread runs on its executor, so signals,
`exit_group`, `execve` drains and host futex wakes all reach it the way they
reach a running thread: `hv_vcpus_exit` on its vCPU. The kick lands in EL1
code; the run loop resumes the vCPU with the kick SGI pending (1a's
critical-section rule); WFI ends; the idle loop acknowledges the SGI and
leaves through `hvc #5`; the executor settles the thread, and its zone wait
takes the signal (EINTR), the control claim or the wake. The signed tests
deliver 200 signals to a thread on a WFI-parked vCPU (all EINTR, handler run
each time, wake p50 about 200 us through the host path) and run `exit_group`
and `execve` with WFI-parked siblings, five times each.

### Hatches and limits

- The zone runs only with the in-kernel GIC: `CARRICK_HVF_GIC=0`, like
  `CARRICK_EL1_FUTEX=0`, turns it off and restores the host futex paths.
- Only the home thread's relative timeouts are served in EL1.
- A thread queued behind a running one waits up to a 2 ms slice unless it
  can move to an idle vCPU; a woken home record on a slot running another
  thread waits the same way (an SGI makes the running slot start the slice).
- A vCPU switches only among threads of the address space installed on it
  (no TTBR switch in EL1 yet), and the slot's run queue holds 8.
- An idle vCPU spins 20 us before WFI: that CPU is spent on every park that
  lasts longer.
- Affinity is honoured for placement; Carrick applies `sched_setaffinity`
  only to the calling thread, and a slot publishes the loaded thread's mask
  at every entry.
- The WFI-to-SGI wake and timer lateness depend on the host thread's QoS
  (below); Carrick sets no special policy on vCPU threads.

## 1d: the guest schedules; host executors drive vCPUs (as built)

Increment 1d makes EL1 the only scheduler of a zone process's threads. A
thread the host makes runnable goes to an EL1 run queue, never to a host
one, and an executor with no thread waits in the guest instead of on a host
condvar. The host executors become per-vCPU drivers: each runs its vCPU,
serves what that vCPU forwards, and loads the threads EL1 sends it. It lands
as `ff4279d18` (run queues, service threads, stealing), `1f7681b09` (the
scheduling switch), two fixes found on the way (`5fddd5a25`, `680b7eef9`),
the two-process test (`c716cc4e7`) and the contract
`kernel.el1.guest-run-queue` (`22d6051a3`).

### Run queues and service threads

- A slot's run queue is an intrusive list through `ZoneRecord::next` under
  the slot lock, unbounded (the 1c limit of 8, and `WakeRefusal::RunQueueFull`,
  are gone).
- A thread runnable on the host's side (a completed host wait, a first run,
  a control action) has no registers in any record: the host keeps its row
  held and allocates a **service record** (`Handback::Service`,
  `alloc_host_runnable`) that stands for it in the guest. `place_from_host`
  queues it on a live slot whose executor can run it (its last slot, an idle
  slot, or the shortest queue). EL1 orders it with the rest; when it reaches
  the head, EL1 does not run it at EL0 but leaves the vCPU for its executor
  (`service_exit`, the idle exit with no thread on the vCPU), which takes the
  head (`take_service_head`) and claims exactly that row and generation
  (`Scheduler::take_zone`). No host run queue holds the thread and no
  executor waits for it on a condvar.
- A thread ready at EL0 that the host woke (a host `FUTEX_WAKE`, the
  `CLONE_CHILD_CLEARTID` exit wake) is queued straight on a slot in the guest
  that runs its address space (`ZoneTables::wake_host`): one compare-and-swap
  from `Parked` to `Queued` under the target slot's lock. With no such slot it
  becomes `Host` with `Handback::Woken` and goes back to its continuation.
- A thread EL1 ran on a vCPU that then exited to the host is its executor's to
  run next (`owe_adoption`, `adopt_zone_handback`).
- Idle vCPUs steal queued threads (`steal`), including service threads; a
  thread the host wants back (`host_wanted`) is never stolen.

### One owner per thread

The claim word is still the only authority, with two changes that keep it so
now that the host places threads in the guest:

- A host claim (signal, control, cancel, timeout) of a thread that is
  **queued** takes it off its run queue under that queue's lock, where EL1's
  switch and a thief also remove it, so exactly one side wins. It keeps what
  the thread resumes with (its wake's result, or its registers); the
  claimant's action follows the resume. Only a thread **running** on a vCPU
  is refused (`El1Held`): its slot is kicked and `host_wanted` makes its
  executor hand it back. The 1c rule (refuse every queued thread and wait for
  its slot's executor) waited forever on an executor serving a long host exit.
- A record the host places in the guest never passes through `Host` on the
  way (`place_in_guest`, `relocate`): a host claimant that sees `Host` takes
  the thread for runnable, so a transient `Host` gave one thread two owners.
  The first version did exactly that and `el1_files_cross_process` died with
  an executor loading a thread whose record EL1 still queued, then an MM
  authority abort at teardown. A spare that parks on the host
  (`retire_slot`) moves each queued thread straight to another slot's queue,
  or hands it back if none can run it.
- A thread ready at EL0 in an address space its slot does not run stays
  queued there (`needs_executor`): when it reaches the head, the vCPU leaves
  for its executor, which takes it (`take_service_head`, counted as
  `foreign_adoptions`) and loads it; an idle vCPU may steal it for its own
  executor. The first version instead moved such threads off a slot that
  installed another address space and, with no slot running theirs, handed
  them back; with many processes they bounced between slots without running.

### Executors

`next_runnable` is the executor's whole choice, in order: the thread it took
off its vCPU at the last exit; the thread at the head of its slot's queue
that needs it (a service thread, or one of another address space); a host run-queue row (`try_take`, which never parks); otherwise it
publishes that it waits in the guest (`WorkerKick::set_guest_idle`, then one
more scan) and runs its vCPU in the EL1 idle loop from the idle entry
(`run_idle_entry_on_vcpu`: the carrier's maintenance root, no address space,
SP_EL1 at the slot frame) until the vCPU leaves for the host. Every host wake
that needs an executor forces a guest-idle vCPU out
(`ExecutorKick::wake_from_guest_idle`, from queue nudges, control pokes,
residency flushes and the host-wait handoff).

A slot is a vCPU's mailbox lease, and a task can carry its lease (the root
process ran on slot 0 whichever executor had it loaded), so an executor may
drive different slots over its life. A slot records the executor that last
published it; an executor that moves to another slot leaves the one it drove
(`leave_slot`: not live, its queue placed elsewhere), unless another executor
took it over. An executor entering a blocking inline host wait vacates its
slot the same way for the wait (`ExecutorKick::host_wait_began`) and revives
it after (`host_wait_ended`). Before both, a service thread placed on a slot
nobody ran waited there: `mmapfileshare_mt` starved its main thread until a
worker's 17 s spin bound ran out, in 7 of 8 runs. A thread the host loads
starts a fresh slice (`reset_slot` clears the slice start); inheriting the
slot's old slice preempted it at the first tick, and `futexforkrequeue` (about
1000 runnable threads) turned slots over five million times without
finishing.

A host placement onto a slot running a thread owes that slot the reschedule
SGI; the host cannot send an SGI, so it forces the vCPU out and the run loop
arms SGI 14 in the vCPU's own redistributor before the next run, with EL0
IRQs unmasked while it is owed (`gic::arm_resched`, `unmask_el0_irqs`). A
completion queued behind a syscall-free loop gets the vCPU within the slice
(`el1_sched_host_woken_thread_preempts_a_compute_loop`).

### Executor count

The default is one executor per guest CPU (`M` = `P`,
`configured_bound_executors`); `CARRICK_BOUND_EXECUTORS=<n>` is the exact
hatch. With the guest scheduling, a second executor on a `P` only adds a host
thread competing for that vCPU's work. Paired runs below: `go build` uses 17%
less carrier CPU than the base binary's host parallelism (`M` = 10), about
what the base binary gives at `M` = `P` (2.78-2.90 s measured earlier), so the
saving is the executor count, not guest scheduling as such.

GMP phase 3 (`handoffp`) is not a precondition of `M` = `P` any more. It was
recorded as one because with one `M` per `P` nothing covered an `M` stuck in a
host call. Now a thread queued on such a vCPU is stolen by an idle vCPU, a
completed host wait is placed on a live slot, and a service thread on a
stopped slot is taken by its executor when it returns. The spares and the
phase 2 handoff (an inline host wait lends its `P`) remain, to keep `P` vCPUs
in the guest while one executor blocks. Two changes keep a lent `P`
returnable when the guest schedules. A spare that borrows a `P` and finds no
thread waits in the guest, and the returning owner forces it out
(`680b7eef9`; before it `go build` wedged in 1 of 2 runs with its stdout
writer parked in `HostWaitToken::resume`). And a spare claims zone work before
it reaches the run queue's release check, so `next_runnable` first returns a
lent `P` whose owner is ready, and a spare that binds a thread on a `P` whose
owner is already ready kicks itself (`99f54dc68`; before it `go-testing`
wedged in 3 of 3 runs, the spare running an idle Go thread on the lent `P`).

### Not done: switching address spaces in EL1

EL1 still runs only threads of the address space installed on a vCPU; an
idle vCPU has none installed. A thread ready at EL0 in another address space
reaches a vCPU through that vCPU's executor, which loads it. Two processes
sharing vCPUs therefore hand off through their executors
(`el1_sched_two_processes_share_vcpus`: 6.2-6.4 host exits and 72-78 us of
carrier CPU per round trip while they contend; with `CARRICK_EL1_SCHED=0`
the same test shows none, because the host run queues run the two processes
one after the other on the pinned vCPUs rather than sharing them).

Switching TTBR0 in EL1 is cheap (42 ns in the spike), but it is not
single-owner without a larger change. Which vCPUs execute an address space is
today owned by executor participation, read by three host authorities: the
exact-MM census that stage-1 pause-modify-resume and the frame-COW sole path
consult (`GuestExecutorCensus`), the fork quiesce that arms COW in the parent
(Task-minted membership), and the crash-snapshot quorum; ASID reuse is
covered by per-executor residency (`AsidResidency`, local invalidation on
each resident executor). A vCPU that EL1 switched into address space Y
without its executor participating in Y is invisible to all four, so a
pause, a fork or an ASID retirement of Y would proceed while it runs Y. The
next increment should make the zone's slot occupancy the one authority for
"vCPU v runs address space Y" and derive all four from it: a zone table of
published address spaces (TTBR0, a fence count, a resident-slot bitmap), EL1
installing Y only after publishing it on the slot and seeing no fence
(Dekker against the host's fence-then-scan), the census, fork quiesce and
crash quorum counting occupied slots, ASID retirement invalidating on the
resident slots' executors, and the executor restoring its loaded task's TTBR
before it runs it. The 6.2-6.4 exits per round trip above are its red
baseline.

### Run state

`/proc/<tid>/stat` renders a zone thread's state from the zone's claim word
where the zone is the authority (`Thread::linux_run_state`): a thread its
executor loaded that is parked in EL1 on its home record reads `S` although
the host still believes it runs, and a thread in a host zone wait that EL1
queued or runs reads `R`. With host run queues a preemption kick of the
"running" thread used to settle it within a quantum; without them it reads
`R` until its vCPU next exits, and `futexforkwakegroups` saw one of 55 futex
waiters as `R` for its whole 5 s bound in half its runs.

### What is still forwarded or host-driven

- Loading a thread that is runnable on the host's side (its registers live in
  the host's task state, not a zone record): its executor loads it when EL1
  reaches its service record (2 service adoptions per round trip of a pipe
  ping-pong).
- Turning a vCPU from one address space to another (above).
- The host-served syscalls themselves (a blocking pipe `read` is a host
  continuation; its completion is what EL1 then schedules), and every
  syscall EL1 does not serve (1b, 1c and the file zone list what it does).
- Signals, `exit_group`, `execve` and ptrace-stops of a thread running on a
  vCPU: the slot is kicked and the thread handed back to its continuation.
- Inline blocking host calls: the phase 2 handoff of the `P` to a spare.
- Residency flushes, ASID invalidation and page-table pauses: host commands
  to executors, which leave the guest to serve them.
- Timers other than the home thread's relative futex timeout: the host
  reactor.

### Hatches and limits

- `CARRICK_EL1_SCHED=0` (exact): host run queues and condvar parks again, the
  futex zone still on; `CARRICK_BOUND_EXECUTORS=<n>`: the executor count.
- An idle vCPU cannot run a thread ready at EL0 of any address space (no
  address space is installed while it idles), so a host completion always
  costs an executor load.
- The guest-scheduling path costs more exits than the hatch on a pipe
  ping-pong (12.8 against 7.3 thousand per 1000 round trips) and about 13%
  more carrier CPU per round trip there (172 against 152 us), for a lower
  round-trip latency (p50 55 against 64 us).
- The zone census (slots, queues, records, counters;
  `ZoneTables::write_census`) is printed by the embed watchdog on a wedge.

## Increment 2, step 1: one authority for which vCPUs run an address space (as built)

Step 1 of increment 2 does the work that "Not done: switching address spaces
in EL1" above names as a precondition. One table now says which vCPUs run
which address space (MM), and every reader of that fact reads the table: the
stage-1 page-table pause, the frame-COW sole-participant check, the fork COW
pause, the crash-snapshot pause and ASID retirement. EL1 still does not
switch TTBR0; that is the next step. It lands as `df7e96ecd` (the table and
the kernel readers), `a623ddf3a` (occupancy per residency, ASID retirement by
broadcast), `d7c408fc9` and `8acfe3f47` (fair entry behind a fenced pause) and
the contract `kernel.mm.address-space-occupancy`.

### The authority

- `carrick_sched_core::Occupancy` holds one word per vCPU execution slot:
  the address-space key the slot runs, or 0. It is `no_std` and valid when
  all zero, so it can later move into the shared EL1 region unchanged. An
  execution slot is the zone slot of the vCPU's mailbox lease, or one of 256
  host-only slots for a vCPU that has no lease (a thread outside the zone,
  or a host executor off the EL1 lanes). An occupied bitmap is kept as a
  scan hint beside the words.
- `carrick_kernel::kernel::mm_occupancy` owns the table's one instance
  and a port per slot (the MM's fence and how to kick the occupant). An
  executor occupies its vCPU's slot for each stretch in which it has a task
  loaded: `occupy_slot` at the top of each poll, and `end_residency` in the
  backend's save, which vacates. A task preempted at a syscall boundary stays
  admitted to its MM but leaves the vCPU. The first signed run tied
  occupancy to admission instead, and the next task loaded on the
  preempting executor's vCPU was refused with `SlotBusy` in three `el1_`
  tests. Blocking host waits vacate too. Editors that run no guest (exec,
  the fork parent, legacy dispatch) occupy nothing.
- Admission (the crash safe-point facet) stays separate from occupancy.
  `MmExecutorParticipation` holds both, as `ExecutorOccupancy::{Editor,
  Admitted, Released}`.

Ordering (Dekker; every access is `SeqCst`):

- An entering executor publishes the slot word, stores its in-guest flag,
  then reads the MM's fence. It parks if the fence is up.
- A pause raises the fence (`PtQuiesce` quiescing), then scans the slots
  running the MM and reads their in-guest flags. It kicks the occupants
  that are in guest and drains them.
- Either the pause sees the entrant's flag or the entrant sees the fence.

A sole stage-1 proof (the frame-COW sole path) is a pause whose snapshot
found no other vCPU. It keeps the fence up, so no admitted peer can enter
behind it. Only a pause that has to drain sets `draining`, which lets the
MM's host waits bail to their run-loop top.

The VM-free stress `a_pause_never_misses_a_vcpu_about_to_run_its_address_space`
runs more installers than slots, switching address spaces on shared slots.
It counts any entry the pauser believed it had drained. With the hint bit
dropped (its negative control), 20 of 22 runs violated.

### What reads it

- **Page-table pause and frame-COW sole check.** `mm_quiesce` acquires
  every stage-1 authority through a `PtQuiesce` pause guard and snapshots
  residents from the table (`MmResidents`). The drain kicks and waits for
  exactly the residents that are in guest. `PtPauseError::UnkickableExecutor`
  is gone: every occupant has a port.
- **Fork.** The COW pause drains every vCPU running the parent's MM,
  whichever process loaded it. Parking the fork parent's sibling threads is
  still task- and registry-based (see Rulings).
- **Crash.** After the lease drain, capture pauses the MM for its snapshot
  (`pause_current_mm_for_capture`). A thread of the dumping process that runs
  on another process's vCPU is kicked back as well; the per-process registry
  alone cannot see it. The MM is shared across processes only across a
  vfork (plain `CLONE_VM` without `CLONE_THREAD` is a COW fork in Carrick).
- **ASID retirement.** It requires the MM to run nowhere, since no task of it
  is left. It then invalidates with one `TLBI ASIDE1IS` on the retiring
  executor's own vCPU. A foreign-COW publication is a per-MM published
  generation. The first vCPU that next runs the MM services it with one
  broadcast invalidation for all vCPUs, and records the generation it read
  before the TLBI as serviced.

### Deleted

- `GuestExecutorCensus` and `kernel/guest_execution.rs`.
- The per-`ExecutorId` residency sets (`AsidResidency` residents and acks).
- The executor pool's acknowledgement fan-out to every resident executor,
  with its worker map and control pokes.
- The paused exact-invalidation phase (`PtInvalidation*`,
  `park_servicing_exact_invalidation`, publish/wait/finish invalidation).
- `ForeignCowInvalidationIdentity` in `carrick-hal`.
- The deferred executor stop.

These proved per vCPU what an inner-shareable invalidation already does for
every PE (Arm ARM D8.13), and they could not name a vCPU that EL1 switched.
The whole step changes 46 files in `crates/` and `fixtures/` with
+3079/-3172 lines.

### Fair entry behind fenced pauses

Every edit is now fenced, including sole ones. A hot mmap/touch/munmap editor
therefore re-elected the moment its pause ended and starved the MM's other
vCPUs. The windowcoherence probe's sibling-handoff scenario (1500 thread
spawns beside two such editors) took 51 s against its 45 s budget; the census
base took 34 s, because its admission lock gave entrants a window.

`d7c408fc9` made each new coordinator wait until every parked entrant had
left the park (6.2 s). That broke the EL1 gate:
`el1_served_burst_surfaces_kicks_under_oversubscription` rounds took about
35 s instead of 3 s, and the worker served 845k-886k lseeks, under its 1M
witness floor. Every pause was now waiting for the host to schedule the
parked executor's thread under oversubscription.

`8acfe3f47` bounds the waiting by refusals. A parked entrant counts the times
it woke at the end of a pause and found the next fence already up. After
`ENTRANT_REFUSAL_LIMIT` (4) refusals, the next coordinator lets every parked
entrant in before it raises the fence. The bound counts only refusals of a
running entrant, so host scheduling delay does not trigger it.

Sibling-handoff time by variant (signed binary):

| Variant | Sibling-handoff |
|---|---|
| Refusal bound of 4 | 5.7-6.0 s |
| 250 us parked-time threshold | 10.5 s |
| 500 us parked-time threshold | 19-23 s |
| 1 ms parked-time threshold (Go's `sync.Mutex` starvation rule) | 44 s |

`el1_served_burst` over 30 rounds:

- With the refusal bound of 4, rounds served 2.0M-4.0M lseeks (median
  3.0M). This matches a build with no waiting at all (1.9M-4.1M).
- A refusal bound of 2 fell below the 1M floor in some round.
- Bounds of 4 or 16 bypassing pauses also fell below the floor in some
  round.

### Findings from the fork/crash and ASID surveys

1. *A vfork child running on a vCPU loaded by a different process escapes
   fork and crash kicks.* This is real only for crash capture: the page-table
   and fork COW pauses were already keyed on the MM. It is closed by the
   crash snapshot pause above. There is no deterministic embed red for it,
   because the harness cannot capture a core. The VM-free red is
   `every_vcpu_running_an_mm_is_counted_whatever_process_it_loaded`.
2. *Zone settle drops a thread parked in EL1 from crash participation
   without stashing its registers.* This is not addressed; see open issues.

### Rulings (cost if wrong)

- **The table lives in host memory in this step.** When EL1 installs an
  address space itself, the table and each MM's fence must be in the shared
  region, and EL1 must follow the same publish-then-check order. If this is
  wrong, the next step moves `Occupancy` (already `no_std` and
  all-zero-valid) and the fence word. The readers do not change.
- **A sole proof is a fenced pause.** It costs one fence raise per sole edit
  and made the entry-fairness work above necessary. If this is wrong, sole
  edits could skip the fence only with some other proof that no admitted
  peer enters mid-edit, and the census used to supply that proof.
- **A broadcast IS invalidation replaces per-executor acknowledgements.**
  It relies on HVF vCPUs of one VM sharing the inner-shareable domain, as the
  Arm ARM requires of PEs. If a host broke that, stale translations after
  ASID reuse would show as wrong-memory reads in the two-process tests.
- **Fork still parks its sibling threads through the task registry and
  lease drain.** Only the COW pause reads occupancy. If this is wrong, a
  sibling that EL1 switched into the parent's MM without a lease would keep
  running during the fork. The COW pause still drains it before any stage-1
  change, so the exposure is register state, not memory.
- **Each slot's port stores the MM's fence.** A kick therefore reaches the
  right `PtQuiesce` without a lookup. If this is wrong, a stale port after a
  slot reuse would kick the wrong fence. Install refuses an occupied port,
  vacate clears the port under its lock, and a scan counts a slot only when
  its port names the same MM and the same fence.

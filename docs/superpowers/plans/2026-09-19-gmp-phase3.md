## Contract

Contract ID: `kernel.scheduler.host-wait-handoff`.
Linux authority: blocking one thread does not prevent another runnable thread
from executing; syscall return values, partial completion, EINTR and restart
remain properties of that syscall. Carrick's structural requirement is that a
host wait relinquishes guest CPU ownership without relinquishing the waiting
task's exact execution generation or moving its thread-affine vCPU.

The public kernel mechanism must support all execution adapters. Scheduling
policy controls placement and ordering but cannot create two owners of a P.
In-zone waits continue to use owned continuations. No host-thread handoff may
replace an in-zone continuation, widen a timeout, poll for progress, or increase
the executor budget to hide starvation.

## Required seams and evidence

| Seam | Required proof |
| --- | --- |
| Public kernel scheduler | Typed single-use host-wait ownership; stale/wrong executor rejected; exact generation retained; spare can run another task on the released P |
| VM-free backend | Public API integration test with two processes and explicit channel/barrier coordination; no runtime/VMM dependencies |
| Scheduling policy | Placement, affinity, pick-next, stealing and ticks retain their contracts during handoff; adversarial and record/replay consumers remain usable |
| Runtime executor | Enter/leave host waits at a safe boundary; preserve TLS, resident registers, kick binding, ASID and audit protocol; never enter guest code without owning a P |
| Dispatch/VFS injection | Host-operation instrumentation surrounds actual external blocking work; guest-dependent operations return owned continuations; injected blocked operation proves progress |
| Observers/auditors/debug | A host-waiting task remains visible and reachable; P current-task is accurate; wake/exit/close accounting and post-mortem explain ownership |
| Embed/testing | Existing builder scheduler hook and TestContainer work; signed guest regression exercises production handoff with default, adversarial and record/replay policies |
| Backend HAL | No HVF type in kernel mechanism; do not transfer an HVF vCPU to another host thread; compile all supported platform closures |
| Conformance | Register VM-free/signed/Docker bindings and structural observations; incomplete bindings explicitly prevent acceptance |

## Initial seam audit and execution state

Current source-local classification and blockers:
[`2026-09-19-gmp-phase3-host-waits.md`](2026-09-19-gmp-phase3-host-waits.md).

- `ExecutorRegistration` and `ExecutorEntry` both copy an immutable
  `Option<GuestCpuId>`. Change the shared authority, not only one copy.
- `RunQueue::take_row` chooses the CPU once, and unconditionally sends spares
  to `park_spare`. A transfer must wake that path and re-evaluate ownership.
- `Scheduler::take` publishes P current-task, while settlement clears it using
  executor binding. A waiting original must never clear a replacement's task.
- Control work and lazy residency flush route by the executor's CPU binding;
  unbound workers use the lifecycle condvar. Transfer must preserve both routes.
- `dispatch_prepared_with_lease` holds exact-mm executor admission through
  dispatch. Moving P ownership while holding this admission can still obstruct
  mm quiescence. Each external wait must release eligible admission before
  blocking and reacquire it in a defined order before accessing guest memory.
- `sync`, `syncfs`, `fsync`, `fdatasync`, and `sync_file_range` in
  `dispatch/fs.rs` are concrete inline external operations to classify; the
  flush handlers call `flush_host_fd` directly. FS backend injection alone does
  not intercept these operations, so the test binding must cover the actual
  production flush seam.
- `carrick-kernel-example::ScriptedBackend` currently creates a scheduler for
  `CarrierWaitService`; its scripted tasks use host threads rather than the
  production executor queue. A generic script semantic pass cannot attest P
  ownership. The new public-API test must explicitly drive registrations,
  claims, handoff and settlement, alongside scripted dispatch coverage.
- `PersistentExecutor::run_until_boundary` is the existing runtime fake
  backend seam. Use it to prove the production loop's return/settlement ordering
  before running signed guest tests.

### Production integration constraints from current code

1. The actual backend trait is `PersistentExecutor` in
   `vcpu_loop/executor/backend.rs`. `run_executor_loop` lends its
   `ThreadExecutionLease` to `ExecutorSubmissionContext` before calling
   `run_until_boundary`; runtime host-wait authorization therefore cannot
   require borrowing a lease still stored in `RunnableThread` at that point.
   Any adapter must authenticate the currently lent lease/binding instead.
2. `dispatch::syscall_requires_execution_lease` currently selects only foreign
   memory/ptrace operations. Ordinary `fsync` has no borrowed lease in
   `SyscallCtx`. Extend an explicit selected-call route or carry an authenticated
   host-wait capability; do not silently treat `None` as authorization and do
   not add a lease mutex acquisition to every syscall.
3. `SyscallDispatcher::with_current_mm_executor_released` already authenticates
   the exact MM and thread lease, removes admission, catches unwind, restores
   the same admission recipe, and revalidates. Reuse its invariant rather than
   introducing an unchecked census decrement. Decide P reacquisition versus MM
   readmission ordering with a regression where the replacement needs a pause.
4. `GuestExecutorParticipation` carries crash-safe-point participation as well
   as page-table census membership. A host wait must preserve a diagnosable
   task and acknowledge crash/quiesce without falsely advertising guest entry.
5. Host reads/writes in `dispatch/fs/rw.rs` can hold an open-description guard
   and can use guest-backed I/O vectors. An operation holding guest pointers
   cannot relinquish the address-space protection those pointers depend on.
   Owned host buffers and pinned endpoint lifetimes are the safe first slice.
6. Host-pipe writes, FIFO opens and record locks already have explicit retained
   continuation state (`BlockingWrite`, `BlockingOpen`, `BlockingRecordLock`).
   Preserve their single-completion and partial-offset rules; a P handoff is
   not permission to turn these guest waits into blocking host calls.
7. `GuestCpu.current_task` is a single optional task even though legacy sizing
   permits multiple bound Ms per P. Host-wait restoration must compare exact
   ownership before clearing/publishing it; a CPU label alone is insufficient.
8. Debug snapshots must represent unavailable/contended ownership as such.
   Never block the abort path on a host-wait return or report an unknown owner
   as an idle CPU. Pending host waits continue to count as live claims.
9. The independent seam audit recommends flush operations as the first binding.
   Its claim that existing FS injection already intercepts the flush is too
   strong: `flush_host_fd` calls libc directly. Its claim that logical guest
   signals automatically interrupt that host call is also unproved. Both need
   actual production adapters and deterministic evidence.
10. `host_file_fd_for_flush` currently returns a bare host descriptor after
    dropping the description guard. Handoff must retain a cloned `HostFdRef`
    (or equivalent owned endpoint) before releasing that guard, so concurrent
    close/reuse cannot redirect the flush. A queued guest fd number is not a
    lifetime proof.
11. Bare stdio is another real external wait seam: `write_stdio_sink` in
    `dispatch/fs.rs` routes inherited descriptors through `write_all_stdio`
    (including an indefinite host `poll` on backpressure) and embedder-provided
    writers through `Write::write_all` under that writer's mutex. Neither may
    be omitted from the final inventory merely because the source labels it
    `BLOCKING-IO-OK`. Captured in-memory output is a distinct, nonblocking arm.
    Preserve ordered bytes, partial-write semantics and caller-writer API;
    establish owned buffer/MM lifetime before making these handoff eligible.
12. The proposed production return order is P reacquisition before exact MM
    readmission, with MM admission released before P handoff on entry. This is
    a design hypothesis requiring a replacement-MM-mutation regression, not
    accepted proof. The existing MM release helper treats readmission failure
    as fatal; a worker's claim that peer exec/exit already lowers it to terminal
    settlement is not established by the current code.

### Direct implementation checkpoint

Three Antigravity drafts were rejected. The owner then requested direct
implementation ("let's complete it ourselves"). Workers are no longer active.
Their production changes were removed before the direct implementation.

The direct mechanism uses one conserved slot per original executor, a shared
placement authority, lifecycle-locked wait predicates, exact registration and
lease authentication, and synchronous guard-drop reacquisition on unwind.
Nested returners reuse the original slot; no second CPU ownership is minted.
Guards cannot move between host threads. Ordinary settlements avoid the
lifecycle lock when no handoff is active.

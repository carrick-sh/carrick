# Native-child entropy (#1338)

The contract `kernel.native.entropy` starts with two runnable red witnesses:
a production native fork leaves parent and child alive, then the child enters
the Linux dispatch pipeline with an eight-byte user buffer and flags zero or
`GRND_NONBLOCK`. The final native entry boundary currently returns errno 38.
The tests are explicitly ignored until the service exists; invoking them with
`--ignored` must fail. This is defect evidence, not acceptance.

## Service design for review

Entropy is a host facility, independent of the file venue. An allowlist change
cannot fix this: `ServiceOperation::Crossing` carries only an ordinal, the
carrier refuses it, and a `Supplied` reply quarantines the ring continuation.
No host task exists for the child to run the root's syscall dispatcher.

Add a neutral, typed entropy service with a bounded ring-owned request/reply
buffer. Reuse the authenticated service-ticket and payload-retention machinery,
with its exact birth, MM incarnation, execution and sequence checks. Do not
encode entropy as a file operation or pass guest user pointers to the carrier.
The shared native process service owns staging and user copyout for both ISAs;
the carrier adapter invokes the existing `proc::getrandom` path against the
staging memory. There must be one implementation of randomness semantics.

The ring must secure the accessible user prefix before asking the host for
bytes. Keep generated bytes and the committed cursor across owner waits; never
replace an already delivered prefix. Cap staging at the existing copyout chunk
bound, including for an enormous requested length. Cancellation must settle the
same service ticket before releasing retained storage.

The current witnesses stop at the immediate refusal boundary. Before enabling
them as success acceptance, drive the asynchronous service ticket through
completion and native resume; a suspended frame still contains its input
registers and cannot yet be checked for a return value.

Also add service encoding roundtrips and invalid
length controls; first-byte EFAULT, accessible-prefix short reads and retained
copyout witnesses; and x86 carrier transport coverage. Shared Rust logic alone
does not prove the x86 physical transport. Signed Node/OpenSSL checks belong to
the director and do not replace these VM-free witnesses.

The root handler now rejects `GRND_RANDOM | GRND_INSECURE` (flags 6 or 7)
before the zero-length fast path or output preparation. The production-dispatch
witness was red at flags 6, length 0: it returned 0 instead of errno 22. A native
Linux diagnostic returned errno 22 at lengths 0 and 8 for both combinations.
The witness also requires zero output preparations and unchanged user bytes.
Linux authority: [getrandom(2)](https://man7.org/linux/man-pages/man2/getrandom.2.html)
and that native diagnostic; Docker differential remains unrun.

Host RNG failure now returns errno 5 before the first commit, or the count
already committed if a later chunk fails. The deterministic bootstrap fallback
is removed: a host facility failure must never silently deliver predictable
entropy. Thread-local fault injection drives the production dispatcher on both the
first and second fill. The witnesses require unchanged uncommitted bytes, one
preparation per attempted chunk and only the committed prefix in the result.
Restoring the old fallback under the same injected failures made both witnesses
red: first-fill failure returned 8 instead of errno 5, and second-fill failure
returned 8192 instead of the committed 4096. These handler corrections do not implement the native-child
service, and neither child witness is enabled as passing acceptance.

Socket and MAP_SHARED file mappings remain separate unimplemented siblings of
this entropy slice. AF_UNIX remains in-zone. Private-file mapping support does
not prove MAP_SHARED support.

## Physical x86 refusal witness

The ignored `cpl0_initial_mm` tests
`serial_host_native_child_getrandom_default_returns_eight_bytes` and
`serial_host_native_child_getrandom_nonblock_returns_eight_bytes` now exercise
the real KVM production pool. Their static assembly fixture forks, calls x86
getrandom (318) in the child with an eight-byte stack buffer, and waits in the
still-live parent. It exits 8 only for an exact eight-byte result, 218 for
ENOSYS (-38), and 91 for other results or lifecycle failures. Native Linux
returns 8 for both flag values; KVM returns 218 for both. These remain explicit
red witnesses, outside the VM-free binding population.

Each test runs its KVM work in a subprocess under `timeout --kill-after=1 10`.
The guest's blocking parent wait cannot outlive that process deadline, even
when no further VM exits occur. The wrapper was checked with a temporary
expected result of 218: both tests completed successfully through the real
KVM fixture. Restoring the expected result to 8 makes them fail again. That
control proves execution and result propagation, not entropy support.

## Implementation entry points still open

The routing request spans a new ABI and retained completion, rather than a
new ordinal match. The existing production paths make the missing work concrete:

- `carrick-core-abi::service::ServiceOperation` needs a typed entropy payload
  and checked encoding/decoding. Its `Crossing` variant carries no arguments
  or output, and `Supplied` is explicitly quarantined by native completion.
- `NativeProcess::begin_service_inner` in
  `carrick-el1-linux/src/native_process_runtime/service.rs` already owns
  service birth, exact member/MM authentication, terminal claims, cancellation
  acknowledgment and retained payload lifetime. Entropy must extend that
  owner, retaining bytes and cursor across copyout waits. `PendingHostFile`
  illustrates the lifetime but is not the entropy venue.
- ARM `NativeServiceStage` and `arm_native_service_exit` in
  `carrick-el1-linux/src/dispatch.rs` stage requests after dispatch. The two
  existing ARM witnesses must be extended through asynchronous completion and
  resume before their return registers can prove success.
- HVF `NativeService` in `metadata_grant/native_service.rs` retains and
  authenticates staged guest payloads for carrier service. The entropy adapter
  must invoke `proc::getrandom` against bounded staging memory, then write its
  reply before acknowledging the same ticket.
- x86 `linux_personality.rs` in `carrick-x86-cpl0` explicitly refuses
  `CompletionRoute::NativeService`. Selecting that route alone still produces
  ENOSYS. Its `anonymous.rs` physical crossing and
  `carrick-x86-cpl0-host/src/cpl0_anonymous.rs` capture/completion are transport
  examples, currently file-specific and restricted to private file mappings.
  Both the CPL0 entry and carrier adapter need entropy transport.

No entropy protocol, staging owner or carrier adapter is implemented here.
The earlier root-handler fixes and these additional witnesses do not satisfy
the issue's child-service acceptance criterion.

## Transport design review constraints

The independent design review agrees with a separate entropy service, with
these requirements before either ISA can claim child-service acceptance:

- Use a fresh checked service operation, with a bounded request/reply record.
  Reject wrapped addresses, oversized requests, impossible returned counts,
  malformed states and nonzero reserved fields. Entropy needs no file or exec
  capability; its requesting member's authenticated service identity is the
  authority.
- Retain the translated payload backing and exact MM incarnation until the
  same ticket acknowledges completion or cancellation. Publish reply bytes
  before acknowledgment. A reused member or stale completion cannot consume
  or overwrite another request's buffer.
- Invoke the existing handler against staging memory. The carrier must never
  use its root task's guest memory or task identity as the child's authority.
- Retain generated bytes and the output cursor across Busy and OwnerWait.
  `OwnedCopyout` provides retention, but its generic fault handling does not
  supply getrandom's committed-prefix short-read semantics. Adapt that
  completion policy before reusing it for entropy.
- Cover asynchronous ARM completion/resume and the physical x86 transport,
  including EINVAL, first-byte EFAULT, accessible-prefix short reads, retained
  copyout, stale identity and cancellation. An ordinal match or the shared
  Rust implementation alone proves neither physical transport.

This is a design review, not approval of an implementation. The child
witnesses remain red after rebasing onto the admitted main revision.

## Flags argument width

The existing handler also rejected high register bits that Linux ignores:
`getrandom` takes `unsigned int flags`. Native x86_64 Linux returned zero or
eight bytes for valid low flags with bit 32, bit 63 or all upper 32 bits set.
Low flags 6 and 7 (conflicting sources), and 8 (unknown flag), still returned
errno 22 regardless of those upper bits. A 72-case raw-syscall diagnostic
checked both lengths and all those patterns, including a zero upper word.

The production-dispatch witness
`getrandom_flags_use_linux_unsigned_int_width` was red at
`flags=0x100000000, length=0`: errno 22 instead of zero. The handler now
narrows the flags argument to its Linux width before validating supported
bits and conflicting sources. The witness checks 54 combinations, requiring
no preparation for zero lengths or invalid flags, one preparation for an
eight-byte valid request, and an unchanged buffer suffix. This handler
correction does not serve a native child's request.

# Admission / crash-reclaim research — 2026-07-05

Deep-research (105 agents, adversarially verified) on crash-safe cross-process admission permits, to redesign carrick's Layer-2 VM-creation gate toward Option 3 (shared-memory counter + death-reclaim) → Option 4 (cap-free, reclaim-only).

## Verified summary

The research strongly validates that Linux's crash-safe reclaim primitives (robust futexes, robust mutexes, OFD locks) are the correct conceptual model — the kernel walks a dying thread's registered robust-list at exit, marks each held lock FUTEX_OWNER_DIED, and wakes a waiter with zero cooperative cleanup, even on SIGKILL/SEGFAULT AND on execve — but ALL of these are Linux-only and unavailable on Darwin. On macOS the picture is confirmed to be barren for lock-side robustness: pthread mutexes have only four types (NORMAL/ERRORCHECK/RECURSIVE/DEFAULT), no PTHREAD_MUTEX_ROBUST/EOWNERDEAD, so a crashed holder deadlocks the shared mutex forever. The single strongest macOS-native primitive that survived verification is the kqueue EVFILT_PROC / NOTE_EXIT (0x80000000) death-watch: a supervising process registers a watch keyed by PID and is delivered a kernel-level death event via kevent(2), giving death-reclaim from the dying process's side without any cooperative cleanup — this is the recommended foundation for carrick's Option 3 (pair a fork-shared shared-memory counter with an EVFILT_PROC supervisor that decrements on NOTE_EXIT). For Option 4 (drop the hard cap), the evidence is that Firecracker — a one-process-per-microVM production VMM structurally analogous to carrick — imposes NO in-process semaphore, permit pool, or fixed concurrency cap, bounding density only by host hardware and delegating per-process limits to cgroups/setrlimit via its jailer; however, Firecracker never faces carrick's synchronous fork-storm pre-block window (its VMs are orchestrated externally, one per process), so its reliance-on-reclaim is not direct evidence that Option 4 survives a burst where every child is runnable before any blocks.

## Findings (confidence / adversarial vote)

### 1. [high, vote 3-0 (claims 0,1,2,3,4,5,6,22 all unanimous)]
Linux robust futexes are the gold-standard model for O(1) low-overhead acquire with automatic crash-reclaim: uncontended lock/unlock never enters the kernel; a one-time per-thread set_robust_list() call registers a glibc-maintained userspace list of held locks (stored simply in current->robust_list); on thread/process exit the kernel walks that list and, for each lock word whose low 30 bits equal the exiting TID, atomically sets bit 30 = FUTEX_OWNER_DIED (0x40000000) and wakes one waiter; the exit-time cost when no list is registered is a single current->robust_list != NULL pointer test, NOT a per-VMA scan; surviving waiters recover via the EOWNERDEAD/pthread_mutex_consistent contract. This requires no cooperative cleanup from the dying process and works even on SIGKILL/SEGFAULT.

> Multiple primary kernel sources verified verbatim: 'the kernel carefully walks the list, and marks all locks that are owned by this thread with the FUTEX_OWNER_DIED bit, and wakes up one waiter (if any)'; '#define FUTEX_OWNER_DIED 0x40000000'; 'the pointer is simply stored in current->robust_list'; noncontended futexes 'can be acquired/released from userspace without having to enter the kernel'; exit cost is 'a simple current->robust_list != NULL comparison' vs the rejected VM method that must 'scan _every_ vma at sys_exit() time'. Value 0x40000000/TID-mask 0x3fffffff confirmed against current torvalds/linux include/uapi/linux/futex.h. Stable ABI since Linux 2.6.17 (2006). Directly models carrick's leaked-counter fix but is Linux-only (not usable on Darwin) and yields robust MUTEXES, not a counting semaphore.

Sources: https://www.kernel.org/doc/Documentation/robust-futexes.txt · https://docs.kernel.org/locking/robust-futex-ABI.html · https://docs.kernel.org/locking/robust-futexes.html · https://man7.org/linux/man-pages/man3/pthread_mutexattr_setrobust.3.html

### 2. [medium, vote 2-1 (single primary source, split vote, high verifier evidence)]
Process-shared robust mutexes reclaim on execve, not just on death: a thread that calls execve(2) while holding a process-shared robust mutex without unlocking triggers the EOWNERDEAD notification to waiters — precisely the class of failure carrick hit, where a fork-child's exec teardown path never ran the counter's destructor.

> man7 pthread_mutexattr_setrobust(3) VERSIONS section states verbatim: 'In the Linux implementation, when using process-shared robust mutexes, a waiting thread also receives the EOWNERDEAD notification if the owner of a robust mutex performs an execve(2) without first unlocking the mutex.' Mechanically sound: Linux mm_release() runs exit_robust_list on both thread exit and execve (address-space replacement). Directly relevant as a REFERENCE model for carrick's exec-teardown failure, but Linux-only — macOS has no PTHREAD_MUTEX_ROBUST, so this is a design pattern to emulate, not a primitive to call. The 2-1 split reflects the macOS-inapplicability nuance, not a factual dispute of the Linux behavior.

Sources: https://man7.org/linux/man-pages/man3/pthread_mutexattr_setrobust.3.html

### 3. [high, vote 3-0 (claims 8,9)]
Open File Description (OFD) locks give crash-safe death-reclaim (freed when the last fd on the open file description closes, which the kernel does on process death) and are owned by the open file description rather than the process — but F_OFD_SETLK is a Linux fcntl feature Darwin does not implement, so it is a reference model only, not a macOS primitive. Note: plain flock (BSD locks), which carrick's incumbent design uses, IS available on macOS and is likewise associated with the open file description and auto-released on death.

> GNU libc manual (primary): 'open file description record locks are associated with an open file description rather than a process' and are 'automatically freed only upon closing the last file descriptor that refers to the open file description.' On process termination the kernel closes all fds, reclaiming the lock with no destructor run — death-reclaim without cooperative cleanup. Caveat: OFD locks (and flock) are INHERITED across fork/CLONE_FILES with the fd, so a forked child sharing the fd keeps the lock alive past the parent's death — directly relevant to carrick's fork-storm context. flock exists on macOS; F_OFD_SETLK does not.

Sources: https://www.gnu.org/software/libc/manual/html_node/Open-File-Description-Locks.html · https://man7.org/linux/man-pages/man2/fcntl.2.html

### 4. [high, vote 3-0 (claims 10,11,12,13)]
macOS/Darwin has NO robust-mutex path (a crashed holder deadlocks a shared mutex forever), but DOES provide a native kernel death-notification primitive — kqueue EVFILT_PROC with NOTE_EXIT (0x80000000) — which is the best-fit macOS building block for death-reclaim of a shared permit. A watcher registers via kevent(2) with ident=target PID, filter=EVFILT_PROC, fflags=NOTE_EXIT and is delivered the exit event by the kernel.

> Apple's shipping SDK header (sys/event.h) verified on-machine: '#define EVFILT_PROC (-5) /* attached to struct proc */' and '#define NOTE_EXIT 0x80000000 /* process exited */'. Apple kqueue(2) man page: 'EVFILT_PROC — Takes the process ID to monitor as the identifier and the events to watch for in fflags ... NOTE_EXIT — The process has exited.' Used in production by libdispatch (DISPATCH_SOURCE_TYPE_PROC) and libuv. Conversely, keith.github.io xcode pthread_mutexattr.3 lists only NORMAL/ERRORCHECK/RECURSIVE/DEFAULT — no PTHREAD_MUTEX_ROBUST/EOWNERDEAD; NORMAL 'will deadlock if reentered', DEFAULT is UB. realm-core #1429 corroborates: 'Apple's platforms do not support robust pthread mutexes' (they had to emulate them). KEY DESIGN IMPLICATION for Option 3: EVFILT_PROC is cooperation-free only from the DYING side — it delivers a notification that a LIVE watcher must act on (do the counter decrement). Caveats: PID-reuse race on late registration; monitoring non-children needs same-uid privilege (trivially met for carrick's forked same-user children); the watcher itself is a new liveness dependency.

Sources: https://github.com/apple/darwin-xnu/blob/main/bsd/sys/event.h · https://keith.github.io/xcode-man-pages/pthread_mutexattr.3.html · https://keith.github.io/xcode-man-pages/kqueue.2.html

### 5. [high, vote 3-0 (claims 14,15,17,18,19,20,21)]
A production one-process-per-VM VMM (Firecracker, structurally analogous to carrick) imposes NO fixed concurrency cap, semaphore, or in-process admission pool on simultaneous microVMs — density is 'limited only by the availability of hardware resources.' Per-process resource bounding is delegated to the host via the jailer using cgroups (v1/v2) and setrlimit (RLIMIT_NOFILE default 2048, RLIMIT_FSIZE), NOT a shared counting pool. There is NO automatic crash-safe reclamation: post-crash cleanup is the operator's responsibility (e.g., cgroup notify_on_release) with acknowledged race conditions.

> Firecracker docs/design.md (primary): 'Each Firecracker process encapsulates one and only one microVM' and 'The number of Firecracker microVMs running simultaneously on a host is limited only by the availability of hardware resources.' README: 'Firecracker consists of a single micro Virtual Machine Manager process.' jailer.md: '--cgroup-version is used to select which type of cgroup hierarchy'; '--resource-limit ... no-file/fsize ... applied by calling setrlimit()'; 'If no limits are provided, the jailer bounds no-file to a maximum default value of 2048'; 'It's up to the user to handle cleanup after running the jailer ... registering handlers with the cgroup notify_on_release mechanism ... while being wary about potential race conditions (the instance crashing before the subscription process is complete).' RELEVANCE TO OPTION 4: this is real evidence a production VMM drops the hard cap and relies on host/hardware limits + reclaim-on-death — BUT Firecracker never faces carrick's synchronous fork-storm burst (its VMs are externally orchestrated, one per process), so it does not validate that reclaim-only survives carrick's pre-block window. A claim that Firecracker uses a fixed footprint-derived slot pool was REFUTED (0-3).

Sources: https://github.com/firecracker-microvm/firecracker/blob/main/docs/design.md · https://github.com/firecracker-microvm/firecracker/blob/main/docs/jailer.md · https://github.com/firecracker-microvm/firecracker

### 6. [high, vote 3-0 (claim 16)]
Time-based leases are a validated model for crash-safe ownership without cooperative cleanup: Firecracker/AWS Lambda's Placement service leases a slot to the Worker Manager for a bounded period, letting the holder act autonomously; a crashed holder's ownership simply expires with no explicit release. This lease/expiry (and by extension heartbeat/generation-counter) pattern is a candidate for carrick when a native death-watch is unavailable.

> NSDI 2020 Firecracker paper (peer-reviewed primary): 'The Placement service uses a time-based lease protocol to lease the resulting slot to the Worker Manager, allowing it to make autonomous decisions for a fixed period of time.' The cited lease reference is Gray & Cheriton SOSP '89 'Leases: An efficient fault-tolerant mechanism' — a lease's defining property is bounded-interval expiry on holder crash with no explicit release. Caveat: Firecracker's lease is a DISTRIBUTED control-plane lease across a fleet, not a local intra-host shared-memory permit — relevant as a design pattern (matching the research goal's 'lease/heartbeat/generation-counter designs') rather than a drop-in local primitive. For a local counter, a lease implies periodic renewal/heartbeat plus reaper scanning for expiry, which trades promptness for a timeout window.

Sources: https://www.usenix.org/system/files/nsdi20-paper-agache.pdf

## Synthesis → design recommendation

**Key fact:** Darwin has NO robust-mutex / robust-futex / OFD-lock (all Linux-only). The one native macOS death-notification primitive is **kqueue `EVFILT_PROC` + `NOTE_EXIT` (0x80000000)** — a watcher `kevent()`s on a target PID and the kernel delivers its exit (used by libdispatch `DISPATCH_SOURCE_TYPE_PROC`, libuv). It is cooperation-free from the DYING side but requires a LIVE supervisor to act on the event.

**Note:** carrick's incumbent `flock` ALREADY gives kernel-automatic crash-reclaim on macOS (freed when the last fd on the open file description closes at process death). So the motivation for Option 3 is not *adding* reclaim — it's a **cheaper acquire** (a userspace CAS vs `open`+`flock`+backoff, which caused the 756k-syscall storm).

### Option 3 (recommended, buildable on macOS)
1. Fork-shared `mmap(MAP_ANON|MAP_SHARED)` region: `AtomicUsize live` + a slot→owner-PID table.
2. Acquire = userspace CAS-increment while `live < budget`, record owner PID. Release (normal) = decrement on vcpu_destroy (exists today).
3. **Death-reclaim:** a supervisor (root carrick) registers `EVFILT_PROC/NOTE_EXIT` on each permit-holding PID; on the kernel exit event it decrements the counter for that PID's slots. Handles exit/crash/SIGKILL — the case flock covers today.
4. **Exec:** `NOTE_EXIT` does NOT fire on `execve` (the PID survives). carrick's `ExecveRebuild` path must EXPLICITLY release the old VM's permit before building the new one (this is exactly the leak the 3b experiment hit — Linux robust mutexes reclaim on exec via `mm_release→exit_robust_list`; macOS needs the explicit code).
5. **Backstop:** a lease/generation reaper (Gray & Cheriton SOSP'89 leases; Firecracker/Lambda Placement uses leases) as belt-and-suspenders for the register-after-already-dead race (finding 5's acknowledged Firecracker race).

### Option 4 (cap-free, reclaim-only) — feasible but carrick-specific risk
Firecracker (one-process-per-microVM, structurally like carrick) runs with NO fixed cap/semaphore/pool — density bounded only by hardware, per-process limits via cgroups/setrlimit. Real precedent that a production VMM drops the hard cap. BUT Firecracker's microVMs are EXTERNALLY orchestrated (one per process) — it NEVER faces carrick's synchronous **fork-storm pre-block window** where every child is runnable before any blocks. So Firecracker is NOT evidence Option 4 survives carrick's burst. Option 4 must be gated on an empirical spike (does reclaim-on-block + the M:N scheduler bound the burst before HVF exhausts?) — the research flags the risk, it cannot clear it.

### Recommended path
Plan **Option 3** (shared-atomic + EVFILT_PROC supervisor + explicit exec release + lease backstop) as a design spike: it is buildable on macOS, gives cheaper acquire than flock, and preserves crash-reclaim. Treat **Option 4** as the aspirational end-state, unlocked only after a fork-storm spike proves the pre-block window is safe cap-free.

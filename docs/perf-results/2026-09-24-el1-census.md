# EL1 census: where the ecosystem rows spend host syscall CPU

Stage 0 of [`2026-09-24-zone-the-workloads.md`](../superpowers/specs/2026-09-24-zone-the-workloads.md).
Supersedes the interim report
([`2026-09-24-el1-census-interim.md`](2026-09-24-el1-census-interim.md)),
which ran on a binary with the EL1 cross-process task-record bug (wrong file
bytes under `go build`, fixed in `fd11bd8cc`).

## Run

- Binary: signed build of `0100bc167`, EL1 on.
- `CARRICK_EL1_CENSUS=<dir> cargo run -p carrick-conformance -- --tier full
  --ecosystem cpython --ecosystem go --ecosystem node --workers 4 --jsonl <file>`.
- Host load: 6.3 at start, 1.3 at the end; not a controlled single-variable
  experiment. Ratios below "suggest"; per-call costs are CPU, not wall.
- 635 rows: 626 MATCH, 5 BUDGET_KILL, 1 non-gating DIFF, 3 gating failures.
  629 runs wrote a census and all 629 joined to their result row.

Gating failures:

| Row | Verdict | Cause |
|---|---|---|
| go-testing, go-time | CARRICK_CRASH | `fault page-table pause failed before mutation: TimedOut`, also seen with `CARRICK_EL1=0`: a wall-clock deadline in the fault path that host load turns into a guest-visible crash |
| go-net_http | TIMEOUT | `TestTransportEventTraceRealDNS` hang, independent of EL1 (tracked separately) |

## Ratio to Docker, matching rows

| Ecosystem | Rows | Median | p90 | Rows over 2x | Sum carrick / sum Docker |
|---|---:|---:|---:|---:|---:|
| go | 191 | 1.34x | 1.39x | 8 | 1.43x |
| cpython | 432 | 1.52x | 2.31x | 83 | 1.37x |
| node | 3 | 1.19x | 1.71x | 0 | 1.17x |

The 91 rows over the 2x bar are short: median gap 723 ms, total 123 s. They
are mostly cpython suites whose Docker time is 300-500 ms.

**These ratios are not paired.** The Carrick times come from this run's four
concurrent workers; the Docker times are the oracle cache's timings from
separate runs. A short row is dominated by that difference: cpython-pprint
measured 1147 ms here (2.85x) but 410-445 ms run alone on the same binary
(about 1.1x its 402 ms oracle). Treat the "over 2x" count as an upper bound
until the rows are rerun paired (one worker, Carrick and Docker interleaved);
the per-call syscall costs below are CPU and do not have this problem.

## Host syscall CPU

Host syscall service is **20.1%** of carrier CPU (234.7 of 1167.8 CPU-s).
Even a free host syscall path leaves 80% of carrier CPU (guest execution,
faults, scheduling) untouched, so syscall work alone cannot close the 2x gap
on the rows that miss it; it is one term, not the term.

forwarded.

## What it says

1. Per-call cost is the pathology, not call count. Linux does rename, unlink,
   brk and a cached openat in single-digit microseconds; carrick's host path
   takes 50-260 µs. By the project's standard these are structurally wrong
   work.
2. openat is the single largest class (18%) and the leading class in most of
   the rows over 2x.
3. The zone's classes (read, write, lseek, inotify) are small on these
   workloads; the file zone's value so far is LTP-shaped (inotify09 2.7 s vs
   36 s off).
4. 80% of carrier CPU is outside syscall service; attributing it (fault
   service, guest compute, scheduling) is needed before promising 2x on the
   remaining rows.

## Consequence for the plan

- Rerun the rows over 2x paired before treating any of them as over the bar.
- Stage 2a: per-call structural budgets for openat, renameat, unlinkat and brk
  (and mmap/munmap), red first, then remove the work that makes them 50-260
  µs.
- Stage 2b: in-zone name resolution for repeated openat/newfstatat.
- Before stage 3: attribute the non-syscall 80% of carrier CPU on the rows
  over 2x (cpython startup), the same way this census attributed syscalls.
- Correctness first: the `fault page-table pause ... TimedOut` deadline is a
  load-dependent verdict and is fixed before any of the above is measured.
